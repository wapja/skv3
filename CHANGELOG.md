# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- Foundation scaffolded from the official Laravel Livewire starter kit (PHP 8.4, Laravel 13.35, Livewire 4, Flux 2, Pest 5).
- Quality toolchain: strict Pint, Rector, Larastan level 8 (incl. component PHP), Pest arch presets and kit rules.
- Composer scripts `setup`, `dev`, `fix`, `check`, `test:pgsql`, `test:browser`; pre-commit hook.
- CI matrix (PostgreSQL 18, SQLite, PHP 8.5) and Dependabot for actions, composer and npm.
- Laravel Boost, `CLAUDE.md`, kit guideline and Claude Code settings with the superpowers plugin.
- Multi-tenancy: organisations on their own subdomain, a strict tenant scope, `Route::tenant()` / `Route::central()` groups, tenant-aware queues and a friendly page for unknown organisations.
- Roles and permissions: a fixed permission catalogue, `permissions:sync`, a global organisation admin role and a super-admin flag with guards against lock-out and privilege escalation.
- Host-aware sign-in: password, two-factor and passkey sign-in only on hosts a user belongs to; failed attempts are rate limited.
- Passkeys that work on every subdomain, password reset links for the user's own host, email changes confirmed by link, and a single-use cross-host sign-in link.
- Email changes and security-page actions (disabling 2FA, removing a passkey, viewing or regenerating recovery codes) ask for a fresh password confirmation.
- Failed sign-ins take at least `AUTH_TIMEBOX_DURATION` (500 ms by default), so response times do not reveal which addresses exist; `TRUSTED_PROXIES` lets rate limits see each visitor's IP behind a load balancer.
- Organisation administration: a wizard that creates an organisation and invites its first admin, editing (only super admins change an organisation's address), archive, restore and purge, and "Open" to sign in on an organisation's own address.
- User administration: search, filters and pagination, an edit page that doubles as the user's profile, status changes, delete and restore. Administrators only manage users whose permissions they hold themselves; changing someone else's address asks for your password and notifies the old address.
- Invitations with roles and language: invite, remind, cancel, copy the invite link and a list of pending invitations. Invitees choose their own name and password on the organisation's address and are signed in right away. Links stay valid for `INVITATION_EXPIRES_IN_DAYS` (7 by default).
- Custom roles per organisation, managed by super admins; the organisation admin and super admin roles are protected.
- Optional impersonation (`MODULE_IMPERSONATION`): sign in as a member with a reason, a banner with a stop button, checked again on every request and fully audited.
- An audit log of sign-ins, security changes and every administrative change, with a filterable viewer and a retention clean-up after `ACTIVITYLOG_RETENTION_DAYS` (365 by default).
- A cross-host sign-in link opened while someone else is signed in asks before it switches accounts.
- A new base layout for every page; light, dark or system appearance is saved per user, without a flash, and is the same on every subdomain.
- Branding with Flux accent colours and an optional logo (`BRANDING_ACCENT`, `BRANDING_LOGO`); an organisation's host shows its name in the brand.
- A collapsible sidebar with three groups (Overzicht, Beheer, Systeem), driven by one navigation definition that hides what you may not open.
- One user menu with settings, language, appearance and log out.
- Dutch and English on every screen and page title: your language is saved in your profile, guests follow their browser and get a language toggle on the sign-in pages.
- Friendly, self-contained error pages (401, 402, 403, 404, 419, 429, 500, 503, and one for every other 4xx and 5xx status, such as 405 when a POST-only address is opened or 502 from a proxy) in the visitor's language, and a clear page for an invitation link that is no longer valid.
- A dashboard with your organisation and roles, counts for users, pending invitations and organisations, recent activity and a getting-started checklist for administrators.
- Optional passkeys module (`MODULE_PASSKEYS`): when it is off, passkey routes, buttons and the settings section are gone.
- An optional Flux Pro layer: with `livewire/flux-pro` installed you get a listbox for roles, tabs, date pickers, a ⌘K command palette and a sign-in chart; without it everything works on free Flux.
- Browser tests in Chromium with the Pest browser plugin (`composer test:browser`), including a CI job.
- The setup engine: `php artisan skv:install` (questions or `--answers=JSON`, resumable, `--force`), `skv:bootstrap` for the Composer and installer hooks, `skv:doctor` (`--fix`, `--json`, also `composer doctor`), `skv:create-super-admin`, `skv:create-organisation` and `skv:flux-pro`.
- A demo seeder with a super admin and the organisations `demo1` and `demo2`, each with an admin, a user and a pending invitation; it never runs in production.
- An installer end-to-end CI job (`laravel new --using` with Herd's flags, then `skv:install`, `skv:doctor` and `composer check`) and `scripts/e2e-local.sh` to run it locally.
- A browser setup wizard at `/welcome-setup`: Herd's *Open site* leads to it, it asks the setup questions with the detected defaults filled in, runs the same steps as `skv:install` one request at a time (the frontend build and Claude Code in the background, the page polling them), shows every manual command with *Copy* and *Re-check*, and ends with a Herd stage that secures the site, shows the summary and signs the new super admin in once. When Herd does not confirm HTTPS in time, *Continue without HTTPS* finishes on http.
- Setup mode: while a local app has no install marker but has its one-time setup token, every web request uses a file session, a file cache and the sync queue, organisation hosts are not resolved, and `/` leads a direct visitor to the wizard until a super admin exists. The wizard answers 404 outside setup mode, without the token and through a proxy or tunnel.
- `skv:bootstrap` writes the one-time setup token while the app is not installed, and prints the address to finish setting up in the browser.
- `php artisan skv:run-step`, a hidden command that runs one setup step in the background for the wizard.
- `npm run build:setup`, which rebuilds the committed `resources/setup/setup.css`, so the wizard renders without `public/build`; CI checks the file is current.
- A local quick login: after a local install with demo data, the login page signs you into a demo account with one click. Accounts that are not active, have confirmed two-factor authentication or no longer use the demo password are not let in.
- A phase-1 CI job and `scripts/e2e-local.sh --entry=…` check the wizard after each of the four entry points (`laravel new` with and without `--database`, `composer create-project`, and a clone with the commands of `composer setup`).
- The doctor's `marker` row fails when the install marker is not valid JSON, instead of the doctor crashing; a repair that throws is reported.
- `/health-check`: a JSON report of the database, the queue, failed jobs, mail and the last backup, authorised by the `X-Health-Check-Key` header, cached for 30 seconds and throttled; 200 when healthy, 503 when a check fails.
- The backups module on spatie/laravel-backup (`MODULE_BACKUPS`, off on SQLite): the database only, an encrypted zip on its own `backups` disk, failure-only mails to `BACKUP_NOTIFY_EMAIL`, a daily monitor, and `pg_dump` found on PATH or in Herd (`PG_DUMP_BINARY_PATH`). Setup writes `BACKUP_ARCHIVE_PASSWORD`.
- The ops schedule (`activitylog:clean --force`, `backup:clean`, `backup:run --only-db`, `backup:monitor`, `queue:prune-failed`, `model:prune`, `auth:clear-resets`), each on one server and never twice at once, with a heartbeat every minute.
- A System page (*System status*, `/system` on the central hosts, super admins only) with the health report, the backups, the schedule and its heartbeat, and the doctor checks that start no process.
- The doctor's `failed-jobs` row (warns while failed jobs are stored) and `backup-password` row (fails while the backups module is on and `BACKUP_ARCHIVE_PASSWORD` is blank; `--fix` writes one); the health check's `last-backup` row fails while backups would be unencrypted, and `backup:run` then refuses to start, also by hand. The `backup-password` row also fails while `.env` has a password that the running configuration lacks (a stale config cache).
- Audit entries written by an Artisan command are tagged with the command, and the audit log shows them as *Command line*, or as the causer's name followed by *via the command line* when they have one.
- `skv:create-organisation --as=<email>` picks the acting super admin.
- `skv:flux-pro` marks `composer.json` with `extra.skv.flux-pro` before it requires the package, so an app that commits Flux Pro on purpose skips the kit's "never references Flux Pro in the committed composer files" test.
- An hourly clean-up (`backup-temp-cleanup`, at :15, also while the backups module is off) removes the files older than six hours that a killed backup left in the package's working directory (`storage/app/backup-temp/temp`); `backup:run` now keeps the temporary directory private (mode 0700), and neither follows a symbolic link; `backup:run` refuses to start with one error line when the directory cannot be private (a symbolic link, a shared or the system temporary directory, or another account's).
- `DB_CONNECT_TIMEOUT` (5 seconds, at least 1, because 0 waits forever) limits how long a PostgreSQL connection may take, so a database that does not answer cannot stall `/health-check` or the System page.
- The System page's *Refresh* and *Run checks* allow six runs a minute per user.
- Per-user limits on sending email-change links (3 per 10 minutes), password changes and two-factor confirmations (5 per minute, every attempt), invitations and reminders (10 per minute), and on the two-factor and passkey management routes (10 per minute); an invitation is sent again at most once per 10 minutes.
- Per-administrator limits on changing another user's address (10 per hour) and on creating organisations, whose first-admin invitation counts under the invitation limit (10 per minute); a refused or failed change or creation saves nothing and does not count.
- Settings → Security lists your sessions: browser and platform, IP address, last activity and *This device*. *Log out other devices* asks for your password (at most 5 attempts a minute), signs out every other session and "remember me" login on its next request, and is recorded in the audit log (*Other devices signed out*). It is hidden during an impersonation.
- Organisations can require a second factor of their members: organisation admins and super admins switch it on the organisation's edit page after confirming their password. An organisation admin needs a second factor of their own before turning it on. The change is recorded in the audit log.
- Members of an organisation that requires a second factor are sent to Settings → Security, with an explanation, until they set up two-factor authentication or a passkey (with passkeys off, two-factor authentication only). `REQUIRE_SECOND_FACTOR_SUPER_ADMINS=true` applies the same rule to super admins on every host. Impersonation sessions and the routes that set up a factor, confirm the password, sign out or hand off are let through; Livewire updates pass only for components of those pages.
- An *Export CSV* button on the activity log: it downloads the entries that match the current filters, from the same organisations the log shows, as a streamed CSV that Excel opens directly. IP addresses and user agents stay empty where the log hides them, cells that look like a formula are neutralised, and every export is recorded in the log and limited to five a minute per user.
- Bulk invitations: paste addresses or upload a CSV file (an email column and an optional language column, with or without a header, comma- or semicolon-separated, at most 512 KB), choose the roles and the language once, check the list (ready, or skipped with a reason) and send up to 100 invitations at a time, at most 100 per hour per administrator; reached from "Invite several people" on the pending invitations page. Addresses that cannot be invited all get the same message. With Flux Pro the file can be dropped on an upload zone.
- Profile photos: upload a JPEG, PNG or WebP (at most 2 MB and 4096 × 4096 pixels) on the profile page. The photo is turned upright, cropped to a 512 × 512 square and stored as WebP without its metadata. It shows in the user menu and the users list, with the initials when there is none. Replacing or removing it deletes the old file, and purging an organisation deletes its users' photos. Not available during an impersonation. With Flux Pro the upload is a drop zone.

### Changed
- `composer setup` runs `skv:bootstrap` and `skv:install`; the temporary development login (`test@example.com`) is gone.
- `permissions:sync` also reports the permissions it strips from the super admin badge.
- When you chose HTTPS and the Herd step could not secure the site, `APP_URL` stays http and the install records `https: false` whether or not passkeys are on (passkeys are switched off when they were on); the summary says how to secure the site later, and the doctor no longer fails on the missing certificate.
- After securing the site, the Herd step writes `APP_URL=https://<folder>.<tld>`, the name it secured (lower-cased), instead of the address setup was started on.
- The doctor step of setup reports the Herd site, HTTPS and the setup token as skipped, because the Herd step runs after it; `php artisan skv:doctor` checks them once setup is done.
- The install marker is written atomically with mode 0600.
- `skv:create-super-admin --password-stdin` reads the password from standard input and replaces `--password=`, so a password never travels in argv.
- `skv:install --answers` also takes `@file` and `-` (standard input), and refuses an inline `super_admin_password` of any type.
- `skv:install` runs only in the `local`, `testing` and `staging` environments.
- `skv:bootstrap` only prepares `.env`, `APP_KEY` and the generated secrets (`HEALTH_CHECK_KEY`, `BACKUP_ARCHIVE_PASSWORD`) for a production install: `.env` or the process environment names an `APP_ENV` outside `local`, `testing` and `staging` (`prod` and `live` too).
- Demo data runs only in the `local` and `testing` environments; elsewhere `skv:install` refuses `start_with=demo` before anything is written.
- The demo accounts use the app's default language.
- `skv:create-organisation --locale` defaults to the app's default language instead of `nl`.
- The setup wizard and the Herd stage answer only requests from this machine (`127.0.0.0/8` or `::1`) without an `X-Forwarded-*`, `X-Expose-*`, `CF-*`, `X-Original-Host`, `Forwarded`, `Via`, `X-Real-IP` or `True-Client-IP` header, check the pinned host on every request, start a new session when the token is accepted (nothing of an earlier session carries over, and its file is deleted), and send `Referrer-Policy: no-referrer` on the Herd-stage pages.
- Without Herd, the wizard refuses an IP address as the host, and setup keeps `APP_URL`'s port. On a host the wizard cannot use, `/` hands out no token: it redirects to the address to use (`http://localhost:<port>/` without Herd, `http://<folder>.<tld>/` under Herd), or answers 409 with a page that names the problem when the folder name is not a valid host name or `herd tld` does not answer.
- The quick login follows the same rule: behind a proxy or tunnel it lists no accounts and `POST /quick-login` answers 404.
- After setup, a super admin who confirmed two-factor sign-in is sent to the login page of the admin host instead of signed in with the single-use link.
- When the Herd step cannot start, the Herd stage shows the command to run yourself; that command is `herd link <name>`, `herd isolate 8.4 --site=<name>` or `herd secure <name>`, whichever the site still needs, and every printed command quotes a name that needs it (also one that ends in a newline or starts with `=`).
- The wizard no longer adds the demo data by default when a super admin already exists, as `skv:install` already refused.
- `skv:create-super-admin --password-stdin` refuses to read a password from a terminal, where it would echo; pipe it in.
- A `HEALTH_CHECK_KEY` shorter than 32 characters counts as no key: `/health-check` answers 403, the doctor's `health-check-key` row fails, and `skv:doctor --fix` replaces it with a random 40-character key; setup and the production `skv:bootstrap` replace it too.
- `/health-check` counts requests without the right key in one shared limit (300 a minute) and requests with it per key (60 a minute), so strangers cannot lock a monitor out; its 429 answers carry `Cache-Control: no-store`.
- The System page and `/health-check` judge the running mail and health-key settings; `skv:doctor` and setup keep reading `.env`. The System page also runs the `apex` check.
- With a PostgreSQL server on this machine the backups prefer Herd's newest `pg_dump` over the one on PATH, use a Herd binary only when it and its directories are no symbolic links, belong to you or root and are not group- or world-writable, and pass the connection's `sslmode` (`DB_SSLMODE`, or the one in `DB_URL`) to `pg_dump`.
- `backup:run`, `backup:clean` and `backup:monitor` hold their overlap lock for 12 hours instead of 24, so a killed backup never skips the next night; `backup:run` refuses an unencrypted backup with one translated error line instead of an exception trace, also for a configuration chosen with `--config`.
- The setup's super-admin password follows the app's password rules (`Password::default()`).
- The Dutch copy says *installatie* and *installatietoken* instead of *setup* and *setup-token*, and the doctor is *Diagnose*, no longer the same word as a check (*Controle*).
- The answers examples keep the answers file outside the project, and `/answers.json` is git-ignored.
- Links the kit builds for another request (password reset, email change, invitation and handoff links) and the passkey origin take their scheme and port from APP_URL, never from the request's port or forwarded headers.
- A failed passkey sign-in is recorded in the audit log like a failed password sign-in (*Sign-in failed*, with `method: passkey`); it names the account only when the passkey belongs to a member of the host's organisation, or on the central hosts.
- A passkey whose signature counter did not increase (a sign of a cloned authenticator) is refused as before and now also writes one warning to the log.
- While you impersonate someone, a language or appearance you pick lasts until the impersonation ends and never changes their account.
- While you impersonate someone, their profile page refuses an email change, so no confirmation link goes out and their own pending link keeps working.
- An email-change link stops working once the account's address is no longer the one the change was requested from, so it never overwrites an administrator's correction made in the meantime.
- The language switch in the user menu reloads the page you are on, query string and filters included.
- `config/app.php` defaults `APP_LOCALE` to `nl`, the same default as the kit's own language setting.
- `skv:bootstrap` creates `.env`, and setup's database step `.env.testing`, with mode 0600 whatever the mode of `.env.example`, also when Composer's install hook (`post-root-package-install`, `composer setup`) creates `.env`; an `.env.example` or `.env` that cannot be read stops them with "Could not read .env." instead of a PHP warning that names the full path.
- `/health-check` keeps its per-key counter under an HMAC of the key with `APP_KEY` instead of a plain SHA-256, and while the ops store is broken it logs one warning line instead of an exception with a stack trace on every request.
- The last-backup health check names why backups would not be encrypted (no `BACKUP_ARCHIVE_PASSWORD`, encryption switched off in `config/backup.php`, or a PHP zip without AES-256), each with its own fix.
- Without the PHP posix extension the backups trust no directory as this account's: `backup:run` refuses to start, Herd's `pg_dump` counts only when root owns it, and the doctor's `pg-dump` row says why. Running as root, `backup:run` accepts only a temporary directory inside `storage/`.
- Every environment except `local` and `testing` uses the strict password rule (12 characters, mixed case, letters, numbers, symbols, not in a known breach), so a staging install's super admin gets it too.
- `skv:flux-pro` also removes the `repositories.flux-pro` entry after an install that did not finish, prints the `composer config --unset` command for a key it could not remove, and cleans up the same way after Ctrl-C or a Composer timeout. It removes only the keys it added, so your own `repositories.flux-pro` entry or other `extra.skv` keys stay.
- New dependency `intervention/image` ^4, through Laravel's own image API on the GD driver, for profile photos. GD needs WebP support; ext-exif is used, when loaded, to turn photos upright.

### Fixed
- CI: `composer audit` reports abandoned packages instead of failing (`config.audit.abandoned = report`); the Composer cache step uses `composer config cache-files-dir`.
- `composer setup` keeps an existing `APP_KEY` (2FA secrets and passkey handles depend on it).
- Setup's Claude step writes the Boost guidelines (`AGENTS.md`) that `CLAUDE.md` imports; `composer setup` never ran `boost:update`, and without the Claude answer no `AGENTS.md` is written.
- Profile emails are stored lower-cased, so a capitalised address no longer locks the user out.
- Real `tests/Feature/ExampleTest.php` and `tests/Unit/ExampleTest.php` are shipped, so the installer's `pest --init` step leaves the test suite green.
- Roles can only be changed through the roles form, never to the super admin badge, another organisation's role or a role with permissions the administrator lacks, and roles of another organisation cannot be edited (skv2 W1).
- Nobody can delete or disable themselves or the last active super admin (skv2 W2).
- Impersonating a pending or disabled user is refused, and an impersonation that is no longer allowed ends cleanly and is logged instead of signing the impersonator out (skv2 W3).
- The pending invitations list keeps working when the inviter was deleted or a user was set to pending by hand (skv2 W4).
- Accepted invitations can no longer be resent, and the accept page says "already accepted" instead of "expired" (skv2 W5).
- The organisation admin role cannot be renamed, deleted or reused as a role name, and organisation admins cannot impersonate each other (skv2 W6).
- A user created without an organisation never becomes a super admin (skv2 W8).
- Deleted users no longer block an address, and the invite and edit forms no longer reveal addresses used in other organisations (skv2 W9).
- Invitation mails are sent only after everything is saved, and a mail failure no longer leaves an orphan pending user (skv2 W10).
- A failed invitation no longer leaves the wrong permission team active (skv2 W11).
- Administrators cannot remove their own admin role, disable themselves or demote the last organisation admin (skv2 W12).
- Invitation tokens are stored once, hashed, with an encrypted copy for the invite link that is removed on acceptance (skv2 W13).
- Invitations need at least one role, and their link works only on the organisation's own address (skv2 W14).
- The admin subdomain is never treated as an organisation, also when `TENANCY_ADMIN_SUBDOMAIN` is changed.
- Downloading recovery codes uses the codes that are stored, and copying them waits for the clipboard and says when it failed.
- The passkey relying-party id always comes from the apex (`Hosts::apex()`) and is lower-cased.
- The kit's own versions of Fortify routes still replace Fortify's when `fortify.prefix` or `fortify.domain` is set.
- A failed passkey check no longer writes a stack trace to the log.
- `composer test:pgsql` uses the same test-database name as the setup and the doctor, also for a folder with a hyphen (`my-app` → `my_app_test`).
- Child processes that setup starts (`npm`, `claude`, the background steps) no longer inherit the project's `.env` values such as `APP_KEY` or `DB_PASSWORD`, and a child `php artisan` reads the current `.env`.
- Setup no longer hangs when Herd does not answer, and reads `herd tld` one way everywhere.
- Setup error messages no longer show PostgreSQL's `DETAIL` lines, which can hold a password hash.
- Setup and the doctor no longer crash on an unparsable `.env`, and read it once per change instead of on every child process.
- A state file that is a symbolic link or cannot be read counts as damaged: the doctor's `marker` row fails instead of the doctor crashing, and a setup token left next to such a marker is still reported.
- `herd.yml`, `.mcp.json`, `composer.json`, `.claude/settings.local.json`, `.env.testing` and the bootstrap's `.env` are written atomically and replace a symbolic link instead of writing through it; a write that fails removes its temporary copy and says which file it could not write, and `.gitignore` covers the copies (`.state-*`) a killed process leaves; the long steps' logs and exit codes are created with mode 0600.
- A re-check of a long step whose process still runs is refused instead of starting it twice, and so is finishing the setup, which would remove the step's files under it (for at most four hours after the step started, so a reused process id cannot block the step for good), and a step that finished between two polls keeps its result.
- The setup errors that still answered 500 (a start that cannot write its state, a long step whose completion check throws, a failure after the marker) show a message the page can act on. An unexpected error behind such a message (a type error, a PHP warning) is also logged with its trace.
- The wizard detects Herd and PostgreSQL once per setup instead of on every poll, and its page title no longer repeats *Installatie*.
- The Herd stage's secret no longer lands in the session as the previous URL, where a reader of the session store could sign in with it.
- The Herd stage's manual page words its advice for the choice made: without HTTPS it offers *Continue* and no longer says passkeys are switched off, and without a Herd command it says there is nothing to run.
- `POST /quick-login` with a malformed email answers 404 instead of 500.
- A Herd step that ends after the login no longer leaves the setup lock behind, and an old Herd exit file no longer times out a new Herd stage at once.
- A re-run with an unchanged super-admin password no longer rotates the remember token or logs a password change, and a secured site with an `http://` `APP_URL` is finished on `https://`.
- The demo seeder creates its super admin, badge and grant in one transaction; setup, `skv:create-super-admin` and the seeder share one creator.
- Setup's step errors and `.env` messages are translated.
- The doctor's `queue` and `failed-jobs` rows are skipped while the database is unreachable instead of reporting a missing table.
- `/health-check` still answers with the real report when the ops store can be read but not written.
- The System page no longer answers 500 when the ops store or a backup disk fails, no longer needs ext-intl for its sizes, no longer boots the console kernel or looks up the PHP binary on every render, and no longer takes the backup lock to show whether a job is on.
- The backups' source connection defaults to the app's default database (`sqlite`), like `config/database.php`.
- The test suite flushes Livewire's per-request state before every test, so an asset one test's page registers no longer shows up in the next test's page.
- A successful sign-in, also with a second factor or a passkey, clears the failed attempts of that address from that IP address.
- An array sent as the address to the sign-in, reset-link and reset routes, as the token to the reset route, or as the credential id to the passkey sign-in, answers with a validation error instead of a server error.
- Failed passkey sign-ins are limited per IP address and failed passkey confirmations per user, whatever credential id the client sends.
- A throttled sign-in returns to the login page, never to the page the Referer names.
- With the passkeys module off, the security page refuses its passkey actions (404) even when a Livewire request calls them directly.
- Recovery codes that can no longer be decrypted (after an `APP_KEY` change without `APP_PREVIOUS_KEYS`) show "Failed to load recovery codes" instead of a server error, on the security page and on download, and "Regenerate codes" stays available to replace them.
- A failed passkey sign-in never names a super admin in an organisation's audit log, also not one promoted from that organisation, and a form post with a malformed credential id no longer answers with a server error.
- The language toggle goes back only to a page on the same host; a `Referer` from another site or another organisation's address leads to the home page instead.
- The message after you are signed out on an address you may not use, after an impersonation ends by itself and after *Stop impersonating* is worded in the language of the page that shows it, no longer in the server's default or the impersonated user's language.
- The email-change mails (the confirmation link and the notice to the old address) and the notice after an administrator changed your address are written in the account's language, also when a queue worker sends them; the email-change mails are queued only once the surrounding transaction commits.
- Changing the language on the profile page shows its confirmation after the reload, in the new language.
- *Try again* on the 429, 500 and 503 pages keeps the address's query string, reloads the page behind Livewire's error dialog, and after a refused form post goes back to the page you came from instead of opening an address that only accepts POST. *Back* on the 403 page only leads to a page on the same host.
- *Reload the page* on the 419 page goes back to the form's page after an expired form post, instead of posting the same expired token again; *Try again* and *Go to the home page* link within the current origin.
- Administrative changes lock their rows in one order (organisation, roles, users, then the rest), so concurrent changes in one organisation wait for each other instead of deadlocking on PostgreSQL. Accepting an invitation while its organisation is archived, disabling or deleting a user during an archive, and changing roles while a role is deleted no longer deadlock. Demoting a super admin or restoring a user while their organisation is archived is refused instead of slipping through.
- A pending invitee keeps the roles they were invited with, also after their only role was deleted.
- Saving a user's name, address and status is all or nothing: a refused status change no longer saves the new name or address, and an address change that fails keeps a pending self-service change link.
- A password reset of a super admin who was promoted from an organisation is no longer recorded in that organisation's audit log.
- The audit log keeps at most 500 characters of a visitor's user agent, as valid UTF-8 without NUL bytes, so an unusual browser header can no longer break the entry of a failed sign-in.
- A queued invitation mail or reminder whose invitation was cancelled, accepted or has expired before the queue worker ran is dropped instead of ending as a failed job.
- Jobs dispatched while a web request runs an Artisan command itself (the setup wizard's migrations and seeders) no longer write *Command line* entries in the audit log.
- The sign-in pages show the organisation's name under the mark on its own address, and the platform name on the central addresses; until now the name was there for screen readers only.
- On a central address, the dashboard's recent activity also lists the entries of archived organisations, as the audit log does.
- Without Flux Pro, a Pro branch that holds `@auth`, `@can`, `@isset`, `@error` or another block with its own `@else` no longer breaks the page; the Flux Pro check reads the views the same way, including tags over several lines, a bound or single-quoted `variant`, Blade comments and a `pro-only` marker that is not right before its `@if`.
- Under Herd, `/` on a host the setup refuses asks `herd tld` once instead of twice, so a Herd that does not answer delays it by at most 5 seconds.
- A Herd step that could not start, or failed, on a site Herd serves with an older PHP now leaves `herd isolate 8.4 --site=<name>` to run instead of ending as skipped, and the Herd stage no longer reports such a site as done.
- The setup's background steps (frontend build, Claude) no longer create `public/build`, `node_modules`, `vendor` or `.claude` readable by their owner only; only the steps' own log, exit and pid files stay private.
- Setup creates the `public/storage` link, so the doctor's `storage-link` row no longer warns after a fresh install.
- Backup archives on the local `backups` disk are readable by this account only (0600, folders 0700).
- `backup:run --config=…` and `--db-name=…` hand `pg_dump` the `sslmode` of the sources that run dumps, not the default configuration's. All of a run's dumps share one `PGSSLMODE`, so when the sources' modes differ the strictest one applies to every source (`verify-full` before `verify-ca`, `require`, `prefer`, `allow`, `disable`), and a mode PostgreSQL does not know makes `pg_dump` refuse.
- `skv:create-super-admin` refuses a password hash given in place of the password, which the `hashed` cast would have stored as it was.
- Accepting an invitation, resetting a password and changing it on the security page refuse a password hash as the new password too, instead of storing it as the account's hash or answering a server error.

### Removed
- Registration, email verification and self-service account deletion (invite-only kit).
- Vite+, Sail, Chisel and `concurrently`.
