# skv3 kit rules

- Livewire components are multi-file (`<name>/<name>.php` + `<name>.blade.php`), never single-file, never with ⚡ in the path. Create them with `php artisan make:livewire` (config defaults to MFC without emoji).
- Full-page components live in `resources/views/pages/**` (`pages::` namespace); reusable ones in `resources/views/components/**`.
- Component classes never call `$this->view()`; pass data with `with(): array` or `#[Computed]` properties.
- Every PHP file declares `strict_types=1`. Run `composer fix` after editing PHP.
- Tests are Pest functions (`it(...)`). Feature tests use `RefreshDatabase` via `tests/Pest.php`. Arch rules live in `tests/Arch`.
- Test files (`*Test.php`) never declare classes, anonymous ones included, and never spell a qualified class name outside their imports: fixtures go in `tests/Fixtures`, because the installer's Pest Drift step (DEC-22) rewrites every class in a `*Test.php` and imports every qualified name (`tests/Arch/TestFileClassesTest.php`).
- Mutation checks copy a file aside with `cp` and copy it back, never `git stash` (the stash is shared by every worktree). After a mutation of a Blade or Livewire component file, run `php artisan view:clear` once it is restored: Livewire recompiles a component only when its source is newer than the compiled class, so a restore in the same second (or with `cp -p`) leaves the mutated class in `storage/framework/views` for later runs and the site.
- Before claiming work is done: `composer check` (SQLite), `composer test:pgsql` (PostgreSQL) and `composer test:browser` (Chromium) must all pass.
- Never use driver-specific SQL (`ilike`, raw `ALTER TABLE ... CONSTRAINT`); use the query builder (`whereLike(..., caseSensitive: false)`).
- Never call `env()` outside `config/`.

## Tenancy and authorization

- Hosts: `{slug}.{apex}` is an organisation, `{apex}` and `admin.{apex}` are central. Group single-host routes with `Route::tenant()` / `Route::central()`; never use `Route::domain()` (the exceptions are the Fortify-mirroring groups in `routes/fortify.php` and `routes/passkeys.php`, pinned by `KitRulesTest`) or a `{tenant}` route parameter.
- Models with `organisation_id` use `App\Tenancy\Concerns\BelongsToOrganisation` and `SoftDeletes` and are listed in `config('tenancy.tenant_models')`.
- Strict mode: reading a tenant model without a bound tenant throws. Bind one with `Tenant::run($organisation, fn () => …)`; read across organisations with `Tenant::bypass(fn () => …)` only in `App\Console`, `App\Setup`, `App\Tenancy`, `App\Actions\Audit` and `Database\Seeders`; Livewire pages are never added to that list. Never remove `TenantScope` with `withoutGlobalScope(s)` / `newQueryWithoutScopes` outside those namespaces; use `Tenant::bypass()`.
- Permissions: use the `App\Authorization\Permission` enum (`$user->can(Permission::UsersView)`, `->can(Permission::UsersView)` on routes); never a permission string. Switch teams only with `withPermissionsTeam($teamId, fn () => …)`.
- Super admin = `users.is_super_admin`, changed only by `App\Authorization\SetSuperAdmin` (pages call `App\Actions\Users\UpdateSuperAdmin`, which authorises first). Organisation roles change only through `App\Actions\Users\UpdateUserRoles`; custom roles only through `App\Actions\Roles\{CreateRole,UpdateRole,DeleteRole}`.
- Tests: `onTenant($organisation)`, `onApex()`, `onAdminHost()`, `asSuperAdmin()`, `asOrgAdmin($organisation)`, `asMember($organisation)`. `Livewire::test()` skips all middleware, so test host rules with HTTP requests. Tests that use `Event::fake()` must keep the tenancy events real (`Event::fake()->except([TenantResolved::class, TenantForgotten::class])`), or the permissions team stays null.
- Sign-in rules live in `App\Tenancy\Auth\HostLoginRule`; never re-implement "may this user sign in here".
- Links that leave the current request (mails, redirects to another host) are built for `Hosts::homeOf($user)`; signed links use `URL::temporarySignedRoute(..., absolute: false)` with `signed:relative`. `Hosts::origin()`, `Hosts::url()` and `tenant_url()` take scheme and port from `APP_URL`; never build a link that leaves the request from the request's scheme or port.
- Moving a signed-in user to another host goes through `App\Actions\Auth\IssueHandoff`; sessions are host-only.
- `password.confirm` on a route does not cover Livewire updates: a Livewire action that changes or reveals a second factor, purges an organisation, switches super admin or changes another user's address starts with `if ($this->passwordConfirmationRequired($returnUrl)) { return; }` (`App\Concerns\ConfirmsPasswords`; build `$returnUrl` with `route(..., absolute: false)` on the server, never from the Referer; it defaults to the security page).
- The self-service and invitation actions that send mail or check a secret (the email change, the password change, the TOTP confirmation, the invite and the reminder; CD-3), and any new action a member can repeat to send mail or test a secret, limit themselves with `App\Support\RateLimits\UserActionLimit` in the component, never in the action (two administrative mail senders have no limit yet: the first admin's invitation from `organisations.create` and an administrator's address change on `users.edit`): `attempt()` before a secret check; `around()` for a send, which reserves the slot, runs the action and gives the slot back when it throws; never a check before and a count after the action, which parallel requests outrun. Code that clears a named limiter's bucket builds the key with `App\Support\RateLimits\ThrottleKey::of()`.
- "Go back" targets in kit code use `App\Http\Support\ReturnUrl::previous($request, $fallback)`, a same-host root-relative path; never `back()`, `url()->previous()` or `url()->current()` in kit code or error views. Vendor `back()` on CSRF-protected POSTs stays (CD-13).
- Any-host pages read tenant models only through `App\Tenancy\HostScope::read(fn () => …)`. `HostScope` scopes tenant models only: filter central tables (organisations, Spatie roles and permissions, `model_has_*`, `sessions`) with `HostScope::organisationId()` and ignore organisation ids sent by the client on a tenant host.
- Administrative actions (users, invitations, organisations, roles, impersonation start) take the acting user as their first argument and authorise themselves with `Gate::forUser($actor)`; session-level actions (`AcceptInvitation`, `StopImpersonation`) and the audit writer take no actor. A transaction locks rows in one order (CD-5), each class at most once: first the organisation (`HostScope::lockForWrite()`, also for archive, `HostScope::lockOrganisation()` for user writes, `Organisation::withTrashed()->lockForUpdate()` for restore and purge), then the roles in id order, then one batch of `users` rows (one `SELECT … FOR UPDATE` on `users` only, no join, in id order: user administration — status, delete, roles, super admin — takes it through `LockoutGuard::lockUsers()` / `lockForRemoval()` and decides on the locked rows, the policy's preconditions included (`ensureStillManageable()`); `UpdateUser` locks the target's row alone; `AcceptInvitation` and `CancelInvitation` lock the invitee's row alone; `ArchiveOrganisation` and `PurgeOrganisation` lock the organisation's users in one statement), then `model_has_roles`, invitations, sessions and reset tokens, activity last; no retry loop. Two accepted exceptions (DEC-34 (5)): `CreateOrganisation` records `organisation.created` before its nested invite, and `PurgeOrganisation` deletes the team's roles after its users. Lock-order tests use `lockStatements()` and skip outside PostgreSQL.
- Livewire components authorise in `mount()` and again before calling an action, keep `#[Locked]` ids instead of Eloquent model properties, and re-resolve the model on every request. Actions that only make sense on a tenant host carry `#[App\Tenancy\Attributes\RequiresTenant]`.
- A non-super administrator acts on a user only when the user's effective permissions are a subset of their own: read them with `App\Authorization\EffectivePermissions` (never Spatie relations on a collection) and decide with `App\Authorization\UserAbilities`, also for index rows.
- A policy method named like an always-checked ability (`impersonate`, `delete`, `forceDelete`, `updateStatus`, `updateRoles`, `updateSuperAdmin`) grants super admins itself; other abilities rely on `Gate::before`.
- Audit entries are written only through `App\Actions\Audit\RecordActivity` with an `App\Enums\ActivityEvent` case; never `activity()`, the activitylog facade or the `LogsActivity` trait. Never log a password, a token or an accept URL. Failed passkey sign-ins are recorded only by `App\Listeners\RecordFailedPasskeySignIn`.
- Invitations are created only through `App\Actions\Invitations\InviteUser`; their links come from `Invitation::acceptUrl()`, built when the queued mail renders. Mails implement `ShouldQueue` and call `afterCommit()`; test them on the sync queue with the `array` mailer, not `Mail::fake()`. Queued invitation mails (`App\Mail\InvitationMailable`) carry the invitation id, not the model, and send nothing when it is gone.
- Impersonation runs only through `App\Actions\Users\{StartImpersonation,StopImpersonation}`; check it with `App\Tenancy\Auth\Impersonation::isActive()`. Tests that depend on the module call `useImpersonationModule(true)` or `useImpersonationModule(false)` first, because CI also runs the suite with `MODULE_IMPERSONATION=false`.
- Every new `__()` key goes into both `lang/nl.json` and `lang/en.json` (`LangCoverageTest`); Dutch copy uses the informal "je".

## UI

- Pages render through `layouts/base` only (the app and auth layouts wrap it); never write `<html>` elsewhere. Two exceptions: error pages extend the self-contained `errors.layout` (*Try again* is `@include('errors.partials.try-again')`), and the setup pages use `layouts/setup`, which must never use `@vite`, `@fonts` or `public/build`, because the wizard runs before the first build (§5.3.4).
- The sidebar's navigation entries go into `App\Support\Navigation\Navigation::items()`, never into a Blade file; the settings sub-navigation (`pages/settings/layout.blade.php`) and the user menu keep their own items.
- Pro-only Flux components appear only inside `@if (Skv::hasFluxPro())`, with a complete free `@else` that binds the same `wire:model` properties. A feature without a free variant (§6.7: the ⌘K palette, the sign-in trend) has a `{{-- pro-only … --}}` comment on the line before its `@if` (or on the same line) instead. The stripper (`FluxProBranches`) and the lint share one Blade grammar, `App\Support\BladeDirectives`, which knows only Blade's built-in conditionals: never put a `Blade::if` condition with an `@else` (spatie's `@role`, `@haspermission`, …) inside a Pro branch. `tests/Arch/FluxProLayerTest.php` checks where Pro tags sit, that the `@else` exists and renders something, and the `wire:model` names.
- Display preferences change through `App\Actions\Settings\{UpdateLocale,UpdateAppearance}`, which keep an impersonator's choice in the session; read them with `Impersonation::localeFor()` / `appearanceFor()` (or `Locales::forRequest()`), never `$user->locale` / `$user->appearance` for display.
- Read the default language with `Locale::default()`, never `config('app.locale')`.
- A status flashed on a redirect that crosses a user switch is translated with `__($key, [], Locales::forNextPage($request, $user)->value)`; on-demand notifications carry the recipient account's language (`->locale($user->locale->value)`) and call `afterCommit()`; a Livewire action that reloads the page flashes its result in the new language instead of `Flux::toast()`.
- Tests that need passkeys call `usePasskeysModule(true)`, because CI also runs the suite with `MODULE_PASSKEYS=false`.
- Browser tests live in `tests/Browser` and pick a host with `->withHost()`; after the first page, navigate with `sameOrigin($page->url(), '/path')`. Run them with `composer test:browser`.

## Setup

- Setup steps (`App\Setup\Steps\*`) resolve every file through `SetupContext::path()`, never `base_path()`, so tests run them against a `setupSandbox()`.
- External commands (`herd`, `npm`, `npx`, `git`, `claude`, `composer`) run through `Process` with `App\Setup\Support\Toolchain::environment()`, and `herd` by its absolute path (`Toolchain::herd()`); under php-fpm there is no PATH. Tests fake every command they expect by name, on Symfony's single-quoted command line (`Process::fake(["*git' 'init'*" => …])`), on top of `Process::preventStrayProcesses()` + `Process::fake([])` and a sandbox `Toolchain`. Never `Process::fake(['*' => …])` or another key that matches every command, a list value, a closure, a variable or a bare `Process::fake()`: each fakes every command. `tests/Arch/KitRulesTest.php` catches only the literal forms (a bare call, a closure, an array that starts with a list value, a literal `'*'` or `"*"` key before the statement's first `;`); a `'**'` key, a list value after a named key or `Process::fake($fakes)` passes it, so never write them. `tests/Pest.php` applies the guard to every test under `Feature/Setup`, `Feature/Console`, `Feature/Backups`, `Feature/Health` and `Feature/System`.
- Project files setup writes (`herd.yml`, `.mcp.json`, `composer.json`, `.claude/settings.local.json`) go through `App\Setup\Support\ProjectFile::write()`, which is atomic and replaces a symlink. A command the kit prints quotes its arguments with `App\Setup\Support\ShellArgument::quote()`.
- "Straight from this machine" is `App\Setup\Http\DirectRequest::isDirect()` (loopback `REMOTE_ADDR`, no proxy headers), for the wizard, the Herd stage and the quick login; never re-implement it.
- Never branch on a Herd exit code alone: parse its output or read the state back.
- The demo seeder (`Database\Seeders\DemoSeeder`) runs only in the `local` and `testing` environments; `skv:install` refuses `start_with=demo` elsewhere.
- A new doctor check is one class per check under `App\Setup\Doctor\Checks`, implementing `App\Setup\Doctor\Check`, and is listed in `Doctor::checks()`, unless it is a health-only check that a fresh install cannot pass (`last-backup`), which goes only in `HealthReport::checks()` (see Ops).
- The wizard and the CLI drive the same steps through `SetupRunner::runStep()`. A new step implements `SetupStep` and sets `isLong()` honestly: a long step runs detached in the browser (`skv:run-step`, polled by the page).
- Wizard code that reads tenant models lives in `App\Setup` (strict mode, `Tenant::bypass()`); the wizard page (`resources/views/pages/setup/**`) and the setup controllers call those services.
- Never write the setup state files by hand. Use `App\Setup\Support\StateFile` and the classes' constants (`SetupToken::PATH`, `WizardState::PATH`/`STEPS`, `HerdState::PATH`/`EXIT`/`LOG`, `Marker::FILE`).
- Wizard tests start with `useSetupWizard()` and never spawn a process: it binds `Tests\Fixtures\InlineStepLauncher`, which runs detached steps inline. Test the page over HTTP (`pageSnapshot()` + `callPageAction()`), because `Livewire::test()` skips the gate and the setup runtime. `useSetupWizard()` switches to the local environment, where CSRF checks run, so forged updates send `X-CSRF-TOKEN`. `useSetupWizard()` also binds a `Detector` without the PostgreSQL probe (`withoutPostgresProbe()`); a test that needs the real probe rebinds `Detector` itself.
- `setupSandbox()` links `public/storage`, so a test of the missing link unlinks it first. `DetachedStepLauncherTest` runs the real launch script with `Process::preventStrayProcesses(false)`, the second exception after `BackupRunTest`. Read env files through `App\Setup\Support\EnvFile`, whose `contents()` refuses an unreadable file.
- Run `npm run build:setup` and commit `resources/setup/setup.css` after changing `resources/views/{layouts/setup.blade.php,pages/setup,setup}` or `resources/css/{theme,setup}.css`, and after updating `tailwindcss`, `@tailwindcss/vite`, `vite` or `livewire/flux` (a Dependabot pull request included); CI checks the file is current. The setup pages never use `@vite`, `Vite::`, `/build/`, `@fonts` or `Skv::hasFluxPro()` (`tests/Arch/KitRulesTest.php`).

## Ops

- A health check is a doctor check (`App\Setup\Doctor\Check`): list it in `App\Support\Health\HealthReport::checks()`, and in `Doctor::checks()` only when a fresh install passes it. `HealthReport` and the System page run checks through `DoctorContext::withoutDetection()`, never `forApplication()`, in web code: detection starts `herd` processes and a PostgreSQL probe. A doctor check the System page runs is listed in `App\Support\Health\SystemChecks::KEYS` and starts no process.
- Ops caches (the health report, the health-check throttle, the scheduler heartbeat, the System page's limiter) use `App\Support\Health\OpsCache::store()`, never the default store, so `/health-check` still answers while the database is down.
- Audit entries written by Artisan commands are tagged automatically (`App\Actions\Audit\ConsoleOrigin`). Never fake a causer for a command.
- Secrets never travel in argv: use `--password-stdin` or `--answers=@file|-`. A new command that takes a secret reads it with `App\Console\Concerns\ReadsStandardInput`.
- Backup tests use `Storage::fake('backups')` and a sandbox `backup.backup.temporary_directory`; only `BackupRunTest` runs a real `pg_dump`. A test that runs `backup:run` past the `--config` resolution restores `PGSSLMODE` with `Tests\Fixtures\PgSslModeSnapshot`. A test that renders the System page binds a sandboxed `HealthReport` and fakes the `backups` disk.
- Tests that depend on the backups module call `useBackupsModule(true)` or `useBackupsModule(false)` first (`true` also sets a test archive password), because the suite runs on SQLite, where the module is off, and on PostgreSQL, where it is on.
- Tests that assert what a command's `CommandStarting` / `CommandFinished` listeners do use `Illuminate\Foundation\Testing\WithConsoleEvents`: without it the console kernel fires no command events under Pest.
- The ops schedule lives in `App\Support\Scheduler\OpsSchedule::define()`, which `routes/console.php` calls; web code reads it through `App\Support\Scheduler\ScheduledTasks`, never by booting the console kernel.
- "This account" checks read the uid through `App\Support\ProcessAccount`, null without ext-posix (tests bind `new ProcessAccount(fn (): ?int => null)` or `fn (): int => 0`).
- `SetSuperAdmin` is called only from `UpdateSuperAdmin`, `DatabaseStep`, `skv:create-super-admin` and `DemoSeeder` (`tests/Arch/AuthorizationRulesTest.php`).
- The health-key rule is `App\Support\Health\HealthCheckKey` (at least 32 characters); never check a key anywhere else.
- Never `exec()`, `shell_exec()`, `system()`, `passthru()`, `proc_open()`, `popen()`, `pcntl_exec()` or backticks in `app/`, `tests/`, `routes/`, `database/`, `config/` or the component classes under `resources/views/` (`tests/Arch/KitRulesTest.php`). Format byte sizes with `App\Support\ByteSize::format()`, never `Illuminate\Support\Number`, which needs ext-intl.
