## Spike outcomes

### DEC-19 — Passkeys package pairing (spike S5)

**Question:** Which `laravel/passkeys` (PHP) / `@laravel/passkeys` (npm) pair do we ship?
**Answer:** The official Livewire starter kit's pairing: PHP `laravel/passkeys v0.2.1` (via `laravel/fortify v1.41.0`, which requires `laravel/passkeys ^0.2.0`), npm `@laravel/passkeys 0.2.0` with constraint `^0.2.0`.
**Evidence:** `composer show laravel/passkeys` (`versions : * v0.2.1`), `composer show laravel/fortify` (`versions : * v1.41.0`), `composer why laravel/passkeys` (`laravel/fortify v1.41.0 requires laravel/passkeys (^0.2.0)`), `node_modules/@laravel/passkeys/package.json` (version `0.2.0`) and `package.json` (`"@laravel/passkeys": "^0.2.0"`) of a fresh `laravel new --livewire` on 2026-10-10. The npm registry already lists `0.4.0`, which the official kit's constraint does not allow.
**Consequence:** Do not bump `@laravel/passkeys` beyond the official kit's constraint until the official kit does. The PHP side (`laravel/passkeys`) is not required directly but resolved through Fortify's constraint, so keep `laravel/fortify` on a version that requires `laravel/passkeys ^0.2.0`.

### DEC-21 — Organisation admin role model (spike S2)

**Question:** Can `organisation_admin` be one global template role (`team_id = NULL`) assigned per team, with pivot primary keys that exclude `team_id` (skv2 D28), on PostgreSQL?
**Answer:** Option A (one global template role) — all three `TemplateRoleTest` tests passed on PostgreSQL: one `organisation_admin` row is assigned in team 1 and team 2 independently, a role can be attached with a NULL team, and a permission added to the template is effective in every team.
**Evidence:** `TemplateRoleTest` on PostgreSQL 18.0 (Herd), spatie/laravel-permission 8.3.0 with `teams => true` and `model_has_roles` / `model_has_permissions` primary keys of (role or permission id, model id, model type) and a nullable `team_id`: all 3 tests passed (9 assertions): assigns one global template role per team; lets a global role be attached with a null team; propagates template permission changes to every team.
**Consequence:** Spec §6.3 option A applies to `UpdateUserRoles`, `permissions:sync`, the doctor check and the roles index (M2).

### DEC-22 — Installer behaviour on a Pest kit without tests.yml (spike S3)

**Question:** What does `laravel new --using` (Herd's flags) change in a kit that already ships Pest, has no `tests.yml`, and keeps CI in `ci.yml` with `matrix.php`?
**Answer:** The installer did not fail on the missing `tests.yml`, but it did two bad things with it. With `--pest`, `installPest()` runs a `str_replace` on `.github/workflows/tests.yml` without checking that the file exists: PHP printed `Warning: file_get_contents(.../.github/workflows/tests.yml): Failed to open stream` (exit code still 0), and the write half of the call then created an empty 0-byte `tests.yml`, which the "Install Pest" commit contains. An empty workflow file is invalid on GitHub Actions. Exit codes of the three runs: `herd-like` (Herd's exact flags: `--database=sqlite --npm --pest --git --boost`) 0, `variant-phpunit` (`--phpunit --no-boost`) 0, `variant-nodb` (no `--database`, `--no-node --no-boost`, no test flag) 0. A first `herd-like` attempt exited 1 for a reason unrelated to the kit rules above: the installer appends ` --no-ansi` (and ` --quiet` with `-q`) to every command it runs when output is not decorated, including each `extra.laravel.installer.post-create-project` command, so my probe hook `@php -r "..."` failed with `Error in argument 3, char 2: no argument for option -`; the probe hook now ends in ` --` so the appended flag is treated as a script argument, and all results below come from the corrected probe. Hook files: `hook-post-create-project-cmd.txt` (written by the kit's Composer `post-create-project-cmd` script) contains `1` in all three runs, because the installer sets `LARAVEL_INSTALLER_DEFER_HOOKS=1` for the create-project phase; `hook-installer.txt` (written by the `extra.laravel.installer.post-create-project` hook, which the installer runs after create-project completes) contains `unset` in all three runs, so the deferral variable is NOT set when installer hooks run. The Pest step (`herd-like` only; with `--phpunit` or no test flag the kit's `tests/` and workflows are left exactly as shipped and `composer.json` is unchanged except for formatting (the rewrite drops the trailing newline), with `pestphp/pest-plugin-drift` still in require-dev): runs `composer remove phpunit/phpunit --dev --no-update`, `composer require pestphp/pest pestphp/pest-plugin-laravel --dev`, `composer update`, `pest --init`, then `composer require pestphp/pest-plugin-drift --dev`, `pest --drift`, `composer remove pestphp/pest-plugin-drift --dev`, then Pint on `tests` and the commit "Install Pest". Net changes: `pestphp/pest-plugin-drift` removed from require-dev (`pestphp/pest` `^5.3` and `pestphp/pest-plugin-laravel` `^5.0` constraints unchanged), all 11 class-based test files under `tests/` rewritten to Pest functions by Drift (the official kit ships class-based PHPUnit tests), `tests/Pest.php` and `phpunit.xml` byte-identical to the kit, plus the empty `tests.yml`. `herd-like.diff` is 1239 lines: 3 hunks of composer.json, 11 test files, `bootstrap/cache/*.php` and `storage/framework/views` (runtime noise), and new files from Boost (`.agents`, `.claude`, `.codex`, `.junie`, `.pi`, `.mcp.json`, `AGENTS.md`, `boost.json`; all but `.codex/config.toml` are already ignored by the kit's `.gitignore`). `composer.json` also gained `laravel/boost` `^2.2` in require-dev (Boost step) and the file lost its trailing newline. `ci.yml` is byte-identical to the kit, so `php-version: ${{ matrix.php }}` (line 12) survived untouched: yes. `configureWorkflowPhpVersion()` only edits `tests.yml` and only the quoted literal pattern `php-version: '8.4'`. `boost:update` entries in `post-update-cmd`: 1 (`@php artisan boost:update --ansi`, appended after the kit's own `vendor:publish` entry; none with `--no-boost`). The installer made its own fresh git repository (4 commits: "Set up a fresh Laravel app", "Install Pest", "Install Laravel Boost", "Configure Boost post-update script"); the kit's `.git` history is not carried over; `--git` was absent in the two variants and they have no `.git`. `variant-nodb` has `database/database.sqlite` and all migrations applied (`users`, `sessions`, `passkeys`, `jobs`, `cache` and so on, 118784 bytes), but the cause is the kit's own `post-create-project-cmd` script (`touch` of the file plus `artisan migrate`): the installer itself deliberately skips migrating for any starter kit and forces `--database` to `sqlite`, and `.env` has `DB_CONNECTION=sqlite` and `APP_URL=http://localhost:8000` in all three.
**Evidence:** `$SCRATCH/herd-like.diff` (summarised; `$SCRATCH` is the spike scratchpad `skv3-spikes`), the three installer logs, the hook files and the decompiled `NewCommand.php` of Laravel Installer 5.31.1 (Herd phar), PHP 8.4.23, Composer 2.10.2, 2026-10-10.
**Consequence:** Kit rules for M1 Task 6 and Task 13: (1) The kit must ship a valid `.github/workflows/tests.yml`; without it the `--pest` run prints a PHP warning and commits an empty, invalid workflow. The cleanest form is a real workflow that already runs Pest and does not contain the string `./vendor/bin/phpunit`; if it contains a quoted literal `php-version: 'X.Y'` the installer rewrites it to the PHP version of the machine running `laravel new` (8.4), so use `php-version: ${{ matrix.php }}` there as in `ci.yml`, which is never touched. (2) Superseded, see DEC-25: the kit ships `tests.yml` as its single workflow and no `ci.yml`. (3) Ship `tests/Pest.php` with `->use(RefreshDatabase::class)` already active (not commented out) and Pest-function tests without a `uses(RefreshDatabase::class);` line, and keep `pestphp/pest-plugin-drift` out of `require-dev`, so every Pest-step edit (comment swap, `uses` removal, Drift conversion, drift removal) is a no-op. Drift on already-converted tests was not run in this spike. `pest --init` recreates `tests/Feature/ExampleTest.php` and `tests/Unit/ExampleTest.php` when they are missing; the recreated feature test asserts `GET /` → 200 (the kit redirects `/`) and Rector flags its untyped closures, so the kit ships real tests at exactly these two paths, which `pest --init` leaves alone ("File already exists", checked against the kit on 2026-10-10). (4) Do not put `boost:update` in the kit's `post-update-cmd`: the installer adds exactly one entry with `--boost`, so a kit entry would duplicate it. (5) Superseded, see DEC-25: the kit keeps `laravel/boost` in `require-dev`; the installer only lowers its constraint, which `skv:install` restores. (6) Any `extra.laravel.installer.post-create-project` command must tolerate a trailing `--no-ansi` or `--quiet`: Artisan commands do, `php -r` needs a trailing ` --`, and a kit hook cannot rely on `LARAVEL_INSTALLER_DEFER_HOOKS` (it is set only for the Composer `post-create-project-cmd` phase, not for installer hooks). (7) `skv:bootstrap` (or the kit's `post-create-project-cmd`) must create `database/database.sqlite` and migrate, because the installer never does either for a starter kit, with or without `--database`. (8) The kit must expect that the installer rewrites `composer.json` (formatting, no trailing newline), commits to a new git history, and generates Boost files (`.agents`, `.claude`, `.codex`, `.junie`, `.pi`, `.mcp.json`, `AGENTS.md`, `boost.json`) that the kit's `.gitignore` already covers except `.codex/config.toml`.

### DEC-23 — Shell tools from the browser wizard (spike S1)

**Question:** Can a php-fpm request under Herd run `herd`, `npm`, `git`, `claude`, and does a detached process outlive the request and the restart caused by `herd secure`?
**Answer:** Two runs on the same probe site. Run 1, php-fpm as it comes: it runs as the normal user (`frankcornet`, `HOME=/Users/frankcornet`) but has no PATH at all (`getenv('PATH')` returns false). Only `git` (`/usr/bin/git`) was found; `herd`, `npm`, `node` and `claude` were not. `npm --version` gave `sh: npm: command not found` (exit 127). The herd script at its absolute path failed with `php: command not found` and `Error finding executable PHP. Quitting for safety.` yet still exited 0, so its exit code cannot be trusted. A detached `herd secure` in that state did nothing (exit file `0`, same error in the log, site not secured, http POST gave 200). Run 2, the probe sets `HOME` (from `getenv('HOME')`, else `posix_getpwuid(posix_geteuid())['dir']`) and `PATH` with `putenv()` before any `exec()`; PATH was `$HOME/Library/Application Support/Herd/bin` (this is also `dirname(PHP_BINARY)`, as php-fpm runs as `.../Herd/bin/php84-fpm`), then `$HOME/Library/Application Support/Herd/config/nvm/versions/node/v22.23.2/bin`, then `$HOME/.local/bin`, then `/usr/local/bin:/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin`. With that environment every tool runs in-process with exit 0: `herd --version` prints `Herd 1.30.2`, `npm --version` prints `10.9.8`, `node --version` prints `v22.23.2`, `claude --version` prints `2.1.296 (Claude Code)`, `git --version` prints `git version 2.54.0 (Apple Git-157)`. A detached process outlives the request in both runs: in run 1 `nohup sh -c 'sleep 15; date >> spawn.log' &` wrote its timestamp after the request had ended, in run 2 a detached `npm --version > npm.out; echo $? > npm.exit` wrote `10.9.8` and `0`. Detached `herd secure skv3-spike` with the explicit environment completed: exit `0`, log `Restarting Nginx...` and `The [skv3-spike.test] site has been secured with a fresh TLS certificate.`, `herd secured` listed the site afterwards, the http request answered 301 about 2 seconds after the request that started it, and https answered 200 at the same moment (2 seconds; polling granularity was 2 seconds). The detached process survived the nginx restart it caused and the php-fpm worker kept working. http POST after securing: `301` with redirect to `https://skv3-spike.test/` (GET gives the same). Caution: before securing, https already answered 200 on Herd's default certificate, so an https 200 alone does not prove the site is secured; check for the http 301 or `herd secured`.
**Evidence:** probe site `skv3-spike.test`, Herd 1.30.2, PHP 8.4 php-fpm, 2026-10-10. Run 1 exit codes: `herd --version` 0 (with error output), `npm --version` 127, detached `herd secure` 0 (with error output, no effect). Run 2 exit codes: all five `--version` calls 0, detached `npm --version` 0, detached `herd secure` 0.
**Consequence:** The wizard must never rely on the PATH of php-fpm (it has none). A small helper builds the environment itself (`HOME` from `getenv('HOME')` or `posix_getpwuid(posix_geteuid())['dir']`; `PATH` as in run 2) and applies it with `putenv()` or an `env` prefix for every child process, and calls herd by the absolute path `$HOME/Library/Application Support/Herd/bin/herd`. The node bin directory is version specific (`.../nvm/versions/node/v22.23.2/bin` here), so the helper resolves it at runtime (the newest directory under `$HOME/Library/Application Support/Herd/config/nvm/versions/node/*/bin`, or a path stored in the wizard state) instead of hard-coding it; `claude` lives in `$HOME/.local/bin`. With that environment: in-process (short, a few seconds at most) are the version and availability checks of `herd`, `npm`, `node`, `claude` and `git`; detached with `nohup sh -c '... > log 2>&1; echo $? > exit' &` (the request returns at once and the browser polls the exit and log files) are `herd secure`, `npm install`, `npm run build` and any other step that can run longer than the 30 second `max_execution_time` or that restarts nginx. The wizard must not trust the exit code of the herd script alone when the environment is wrong, so it checks the log text and verifies the result (http 301 or `herd secured`). After `herd secure` the wizard must navigate with a GET (a POST to the http URL is answered with a 301 and loses its body), and it must wait for the http 301 before sending the browser to https. This refines spec section 5.3.4 ("Herd step"), which polls the https origin of `/up` with `fetch(..., {mode: 'no-cors'})`: that poll is unreliable, because https answers 200 on Herd's default certificate before the site is secured (and a no-cors fetch cannot read the result or see a certificate problem). The "secured" signal reaches the browser as follows: the detached step writes its exit code and log to the step status file (`storage/logs/skv-herd.log` plus an exit file); the page polls a server-side status endpoint on the http origin, which reads that file, confirms with `herd secured` (or a server-side http probe of the site that expects a 301) and only then reports done; the page then navigates with a full GET to the https URL. `herd isolate` was not tested. `StepResult::manual()` stays for the cases where the environment check fails (a tool missing from the resolved PATH, for example `claude` not installed or no node under Herd's nvm directory), where the exact command is shown for the user to run in a terminal; `herd share` and anything that needs a login also stay manual.

### DEC-24 — Headers added by `herd share` (spike S6)

**Question:** Which request headers mark traffic tunnelled through `herd share`?
**Answer:** Not testable: `herd share` starts Expose, which asked for a login (`Opening your browser to login or create an account`, with a device code URL on `expose.dev`) and sat on `Waiting for authentication...`, so no public URL was printed within 15 seconds. No account or token was created. For comparison, a direct local request to the Herd site has `REMOTE_ADDR` `127.0.0.1` and only the headers `HTTP_ACCEPT`, `HTTP_USER_AGENT` and `HTTP_HOST` (no `HTTP_X_*`).
**Consequence:** The wizard keeps the access gate of spec section 5.3.4: it rejects (404) requests carrying `X-Forwarded-For`, `X-Forwarded-Host`, `X-Original-Host` or any `X-Expose-*` header. Two additions beyond the spec, `X-Forwarded-Proto` and `Forwarded`, may be rejected as well, because they are standard headers of other reverse proxies and tunnels and a local Herd request never carries them (this is a choice, not something observed). The request IP is deliberately not a gate (as in the spec): under Herd every request, including `herd share` traffic, arrives from `127.0.0.1`, so a `REMOTE_ADDR` rule would reject nothing. Because `herd share` was not testable, the real header names stay unconfirmed and the `X-Expose-*` pattern remains a spec assumption. The one-time token remains the primary gate.

## Build decisions

### DEC-25 — Build rulings and carried follow-ups (M0–M1)

**Question:** Which decisions taken while building M0 and M1 change or refine the spec, the plan or DEC-22, and which smaller findings are carried to later milestones?
**Answer:** (1) The kit has one CI workflow, `.github/workflows/tests.yml`, and no `ci.yml`. With `--pest` the installer edits `tests.yml` without checking that it exists and commits an empty, invalid file when it is missing (DEC-22); a real `tests.yml` that sets PHP via `matrix.php` and never contains `./vendor/bin/phpunit` turns every installer edit into a no-op and avoids two workflow files. (2) `laravel/boost` stays in `require-dev`, because the kit's own Claude setup needs it; the installer's `composer require laravel/boost:^2.2 -W` only lowers the constraint, which `skv:install` restores (spec §5.2). (3) The kit's `post-update-cmd` has no `boost:update`, because the installer appends one with `--boost` without a duplicate check (`skv:install` adds it in M6); superseded in part, see DEC-33 (11): `composer setup` runs no `boost:update`, and `AGENTS.md`, which `CLAUDE.md` imports, comes only from setup's Claude step. (4) `.gitignore` keeps the other agents' directories ignored (`.agents`, `.cursor`, `.junie`, `.codex` and so on) and only `CLAUDE.md`, `boost.json`, `.claude/settings.json` and `.ai/` are committed, because Boost may generate files for other agents (DEC-22 rule 8). (5) Changing the profile email applies without proof of ownership; email verification is off by design, so `email_verified_at` gates nothing. This is a known risk (a typo locks the user out; a hijacked session can move the account to an attacker's address). M3 must confirm a new address through a signed link sent to that address and notify the old address before the change is applied. Emails are lower-cased on save since M1. (6) Claude Code permissions are an explicit allow-list of safe artisan commands (`test`, `route:list`, `config:show`, `about`, `view:clear`, `config:clear`, `boost:update`, `list`, `dev:list`) plus the quality tools, composer scripts and npm. `tinker`, `migrate` and `db:seed` are not allowed, so they prompt. Denied: `migrate:fresh`, `migrate:reset`, `migrate:refresh`, `migrate:rollback`, `db:wipe`, `herd sites` and the Herd MCP tool `get_all_sites` (both dump every site's `.env`), and reading `.env` files (`.env.example` stays readable). The deny rule for the Herd MCP tool only matches a server named `herd`, so M6 must register the Herd MCP server under that name. Allow rules of the form `Bash(php artisan make:*)` are not used, because a trailing `:*` means "followed by a space" and never matches colon subcommands such as `make:model`. (7) The PostToolUse Pint hook is synchronous and calls `"$CLAUDE_PROJECT_DIR"/vendor/bin/pint`: an asynchronous Pint run can rewrite a file between two edits and cause "file modified since read" errors, and Pint on one file is fast.
**Evidence:** DEC-22 (installer behaviour), the M1 security review of `.claude/settings.json`, the whole-branch review of M0–M1 (2026-10-10), the Claude Code permission and hook documentation, and `tests/Feature/Tooling/{CiWorkflowTest,AiConfigTest,ComposerScriptsTest}.php`.
**Consequence:** The spec (§3, §4.2, §5.2, §5.3.3, §5.3.4, §8, §9, §11.2, Appendix A) and the plan's Global Constraints were amended to match; DEC-22 consequences (2) and (5) point here. The follow-ups below are carried to their milestones.

### DEC-26 — Tenancy and authorization build rulings (M2)

**Question:** Which choices made while building M2 refine the spec, and what is deferred?

### DEC-27 — Authentication build rulings (M3)

**Question:** Which choices made while building M3 refine the spec, and what is deferred?
**Answer:** (1) One `App\Tenancy\Auth\HostLoginRule` (active, not deleted, belongs to the current host; super admins everywhere) gates password sign-in (Fortify `authenticateUsing`, memoised on the request because Fortify calls it twice; an unknown address still costs one password hash, and every failure is padded to `auth.timebox_duration`, 500 ms by default (`AUTH_TIMEBOX_DURATION`), which must stay above one bcrypt hash at `BCRYPT_ROUNDS` on the production hardware; the same setting pads Laravel's password-reset broker and `SessionGuard`), the two-factor challenge (`UnscopedTwoFactorLoginRequest`), passkeys (`Passkeys::authorizeLoginUsing`), password resets (`ResetUserPassword`, so a disabled or pending user cannot set a password through a reset link) and handoff links (`HandoffController`). An unknown address, a wrong password, an inactive user and a user on a foreign host fail identically. (2) The login, two-factor and passkey limiters count failed attempts only (§4.2), through `Limit::after()` (a response of 400 or more, or validation errors flashed by this request): login per address+IP (5/min) and per IP (20/min), two-factor per challenge (`login.id`, 5/min), passkeys per signed-in user, or per IP for a guest's sign-in (10/min; amended by DEC-34 (3), G1-05). A failure-only limit is checked before and counted after the response, so parallel requests can outrun it; each therefore has a backstop that counts every request, set above what one real user reaches: `login-burst` 30/min per address+IP, `two-factor-burst` 10/min per challenge, `passkeys-burst` 30/min per IP. The IP-wide login limit has no backstop, so a parallel spray over many addresses from one IP can exceed 20 failures a minute (each address stays capped at 30). Password confirmation (5/min per user), reset-link requests (`password-email`), password resets (`password-reset`; both 5/min per address+IP and 20/min per IP) and handoff links (10/min per IP) count every request. `password.email`, `password.update` and `password.confirm.store` are throttled by redefining Fortify's routes with the same method, URI and name, so a custom `fortify.prefix` or path would bring the unthrottled vendor routes back. The IP limits assume `$request->ip()` is the client's address: behind a load balancer or CDN, set `TRUSTED_PROXIES` (`config/trustedproxy.php`, empty by default). (3) Passkeys: the relying-party id is `PASSKEYS_RELYING_PARTY_ID` ?: `TENANCY_APEX_DOMAIN` ?: the APP_URL host, set in `config/fortify.php` because Fortify copies `fortify.passkeys.*` into `passkeys.*` once at boot. The allowed origin is set to the request origin by the `App\Tenancy\Listeners\SetPasskeyOrigin` listener on `TenantResolved` and `TenantForgotten` (§4.2, §6.2; `CurrentTenant::forget()` always dispatches, so central hosts get it too, and §6.8 switches the listener off with the module). It reads the request, not the tenant, so the value stays the browser origin inside `Tenant::run()`. (4) `UnscopedPasskey::user()` loads users without the tenant scope and including deleted users, so the host rule can refuse them (the package dispatches `PasskeyVerified` with the user before the authorisation check). This replaces §4.2's `Passkeys::useUserModel()` with an unscoped user model: overriding the passkey's relation (DEC-26 (16)) does the same without a second user model. WebAuthn ceremony failures render as 422 on `credential` instead of 500. (5) Password reset links are built with `Hosts::url(Hosts::homeOf($user), …)`: what `tenant_url()` builds for members (§4.2), and the admin host for super admins. Every reset-link request answers the neutral `passwords.sent` in the same time, because `SendPasswordResetLinkController` runs the broker after the response through `defer()`; there is no separate neutral response class, since nothing resolves Fortify's failed reset-link response once its route is replaced. A failed reset always answers `passwords.token` and takes at least `auth.timebox_duration` (longer than the token's hash check), so `password.update` does not reveal whether an address exists, and a reset token is refused for a user who may not sign in on this host (1). (6) `AuthenticateSession` runs in the web group, so it also covers Livewire updates. (7) Email change: a 60-minute signed link (`signed:relative`, on the user's home host) carries a nonce whose hash is cached per user. The stored hash is compared first and forgotten only when it matches, so an older link never removes the newest one: only the newest link works, and only once. The signed-in user must be the link's user; the old address gets a notice at request time, routed to the address itself (not the user model) so a late queue run cannot send it to the new address; `email_verified_at` is removed (verification is off by design). The link proves control of the new address only, so `email-change.confirm` also runs `password.confirm`: the change applies only after a password confirmation within `auth.password_timeout`, as on the security page, and a hijacked session whose confirmation has expired cannot move the account to an attacker's address (DEC-25 (5)). Inside that window the session can change the address, as it can change the second factors (10); a second factor alone would not have stopped the takeover, because the same session could turn 2FA off. (8) Handoff tokens live in a central `handoff_tokens` table (sha256 hash of a random 64-character token, 60 s, target host, relative path); this stands in for §6.4's "signed token" and is at least as strong. `App\Actions\Auth\IssueHandoff` decides only whether the target host is the user's (members: `Hosts::homeOf()`; super admins: the apex, the admin host or an existing organisation's host); whether the user may still sign in is decided when the link is used, by the host rule. `Hosts::slugOf()` parses `{slug}.{apex}` for both `IssueHandoff` and `SubdomainResolver`. Tokens are consumed atomically by an update that must affect one row, always start a clean session (nothing carries over from an earlier user), and dispatch `HandoffConsumed` for the audit log. (9) A SyncQueue-based job's (`sync`, `deferred`) `failed()` hook runs in the job's context: JobTenancy ignores `JobExceptionOccurred` for a `SyncJob` that is not yet deleted, and `JobFailed` restores. The bypass arch rule also catches `TenantScope` removed by name or by instance, and `suspendBypass()` / `resumeBypass()`. (10) `password.confirm` guards the security page request only: Livewire updates skip route middleware, and a component snapshot from any account can call an action with another session. Every Livewire action that changes or reveals a second factor (disable 2FA, start or confirm the 2FA setup, regenerate or download recovery codes, delete a passkey) therefore checks the confirmation again through `App\Concerns\ConfirmsPasswords` and otherwise sends the user to `password.confirm` and back. `RequirePassword` as Livewire persistent middleware was not used: Livewire acts only on a redirect from persistent middleware and ignores the 423 JSON answer that `RequirePassword` gives a request sent with `Accept: application/json`.
**Evidence:** `tests/Feature/Auth/*` (HostScopedLogin, LoginThrottle, Passkey with a software authenticator, PasswordResetHost, AuthenticateSession, Handoff), `tests/Feature/Settings/{EmailChange,RecoveryCodes,ProfileUpdate,SecurityActions}Test.php`, `tests/Feature/Tenancy/QueueTenancyTest.php`, `tests/Arch/TenancyRulesTest.php`; vendor reads of Fortify 1.41 (`AuthenticatedSessionController`, `RedirectIfTwoFactorAuthenticatable`, `FortifyServiceProvider::configurePasskeys`), laravel/passkeys 0.2.1 and web-auth/webauthn-lib 5.3 (`CheckAllowedOrigins`).
**Consequence:** Deferred: M4 — audit logging of sign-ins, failures, password resets, 2FA and passkey changes and `HandoffConsumed`; the organisations "Open" action and slug-rename redirect that issue handoffs. M5 — the passkeys module flag and its UI (§6.8), Dutch copy for the existing Fortify/Flux auth screens, error pages. M7 — the sessions list and "log out other devices" UI, scheduling `model:prune` for handoff tokens. Optional, not scheduled: an "address changed" notice to the old address from `ConfirmEmailChange` (7), and a doctor check that one bcrypt hash at `BCRYPT_ROUNDS` stays below `auth.timebox_duration` (1).
