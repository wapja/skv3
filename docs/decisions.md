# Decisions

Owner decisions from the design spec (`docs/superpowers/specs/2026-10-10-skv3-design.md` §2) and decisions made during the build. Newest last.

## Owner decisions

| ID | Topic | Decision |
|---|---|---|
| DEC-01 | Multi-tenancy | Always on (subdomain per organisation), as in skv2. |
| DEC-02 | Flux Pro | **Optional layer.** The kit works fully on free Flux. Pro features switch on when `livewire/flux-pro` is installed. The owner's licence tier is unconfirmed, so Pro is not a hard dependency (§6.7). |
| DEC-03 | Database | PostgreSQL by default (Herd Pro). SQLite is a fully supported fallback when no Postgres is available. Both run in CI. |
| DEC-04 | Language | UI defaults to `nl`, with complete `en`. Code, comments, README, spec and agent guidelines are in English. The end-user manual is in Dutch under `docs/`. |
| DEC-05 | Livewire component format | Multi-file components (skv2 D34), no ⚡ emoji. Component PHP is analysed by Larastan and Rector (§7.1). |
| DEC-06 | Strictness | Larastan level 8, no baseline (aim for max in v1.x). Pint = laravel preset + `declare_strict_types`, `strict_comparison`, `ordered_class_elements`. No blanket `final` rule; no Pest `strict()` preset. |
| DEC-07 | Debug tooling | Debugbar + Pail + Herd Dumps/Log Viewer. No Telescope. |
| DEC-08 | Optional modules | Passkeys, backups, impersonation are runtime modules (§6.8). Demo data is a setup choice. Everything else is core. |
| DEC-09 | Distribution | Public GitHub + Packagist. Entry points: Herd wizard / deep link, `laravel new --using`, `composer create-project`, `git clone` + `composer setup`. |
| DEC-10 | Setup approach | Browser setup wizard + CLI counterpart, both driven by one set of idempotent setup steps (§5). |
| DEC-11 | v1 scope extras | Sessions list + "log out other devices", "second factor required" per organisation, audit log CSV export, bulk invitations, avatar upload — all in v1 (milestone M7, §6.6). |

| DEC-13 | Organisation membership | One organisation per user; email globally unique among non-deleted users. |
| DEC-14 | Audit retention | `ACTIVITYLOG_RETENTION_DAYS` (default 365), clean command scheduled (§4.9). |
| DEC-15 | PHP floor | `^8.4` (Pest 5 / PHPUnit 13 / activitylog 5.1). CI also runs PHP 8.5. |
| DEC-16 | AI files | Commit a hand-written `CLAUDE.md`, `boost.json`, `.claude/settings.json`, `.ai/**`. Gitignore `AGENTS.md` (Boost-generated), `.mcp.json`, `.claude/settings.local.json`. |
| DEC-17 | Starting point | Scaffold from the latest official Laravel Livewire starter kit, then reshape (as skv2 D3). |
| DEC-18 | Release channel | `main` is the release channel: the installer always installs the default branch (§5.2). `main` is protected; work happens on feature branches; semver tags are added for `composer create-project` users. |

## Spike outcomes

### DEC-19 — Passkeys package pairing (spike S5)

**Question:** Which `laravel/passkeys` (PHP) / `@laravel/passkeys` (npm) pair do we ship?
**Answer:** The official Livewire starter kit's pairing: PHP `laravel/passkeys v0.2.1` (via `laravel/fortify v1.41.0`, which requires `laravel/passkeys ^0.2.0`), npm `@laravel/passkeys 0.2.0` with constraint `^0.2.0`.
**Evidence:** `composer show laravel/passkeys` (`versions : * v0.2.1`), `composer show laravel/fortify` (`versions : * v1.41.0`), `composer why laravel/passkeys` (`laravel/fortify v1.41.0 requires laravel/passkeys (^0.2.0)`), `node_modules/@laravel/passkeys/package.json` (version `0.2.0`) and `package.json` (`"@laravel/passkeys": "^0.2.0"`) of a fresh `laravel new --livewire` on 2026-10-10. The npm registry already lists `0.4.0`, which the official kit's constraint does not allow.
**Consequence:** Do not bump `@laravel/passkeys` beyond the official kit's constraint until the official kit does.

### DEC-20 — Pro-only Flux components (spike S4)

**Question:** Which Flux components exist only in `livewire/flux-pro`?
**Answer:** Top-level Pro-only components (22): `accordion`, `autocomplete`, `calendar`, `carousel`, `chart`, `color-picker`, `command`, `composer`, `context`, `date-picker`, `editor`, `file-item`, `file-upload`, `kanban`, `phone`, `pillbox`, `popover`, `slider`, `tab` (with `tab.group`, `tab.panel`), `tabs`, `time-picker`, `timeline`. Pro-only files inside the shared `select` folder (17): the `combobox`, `custom` and `listbox` variants (`select/variants/combobox`, `select/variants/custom`, `select/variants/listbox`) plus their parts: `select/button`, `select/empty`, `select/group/variants/custom`, `select/indicator/index`, `select/indicator/variants/check`, `select/indicator/variants/checkbox`, `select/indicator/variants/radio`, `select/input`, `select/option/create`, `select/option/empty`, `select/option/variants/custom`, `select/options`, `select/search`, `select/selected`. The free `select` only has the `default` variant (native select). No other shared folder contains Pro-only files; every other Pro file lives in one of the Pro-only top-level folders above.
**Evidence:** `comm` of `flux` v2.20.1 vs `flux-pro` 2.20.1 stub folders (`vendor/livewire/{flux,flux-pro}/stubs/resources/views/flux`) in the official Livewire starter kit scaffold, 2026-10-10.
**Consequence:** These names may only be used inside `@if (Skv::hasFluxPro())` branches (spec §6.7). The lint test in M5 uses the free stub folder as its allow-list, so this list is informational.

Appearance persistence: confirmed `flux.appearance` key in `vendor/livewire/flux/src/AssetManager.php`.

### DEC-21 — Organisation admin role model (spike S2)

**Question:** Can `organisation_admin` be one global template role (`team_id = NULL`) assigned per team, with pivot primary keys that exclude `team_id` (skv2 D28), on PostgreSQL?
**Answer:** Option A (one global template role) — all three `TemplateRoleTest` tests passed on PostgreSQL: one `organisation_admin` row is assigned in team 1 and team 2 independently, a role can be attached with a NULL team, and a permission added to the template is effective in every team.
**Evidence:** `TemplateRoleTest` on PostgreSQL 18.0 (Herd), spatie/laravel-permission 8.3.0 with `teams => true` and `model_has_roles` / `model_has_permissions` primary keys of (role or permission id, model id, model type) and a nullable `team_id`: all 3 tests passed (9 assertions): assigns one global template role per team; lets a global role be attached with a null team; propagates template permission changes to every team.
**Consequence:** Spec §6.3 option A applies to `UpdateUserRoles`, `permissions:sync`, the doctor check and the roles index (M2).

### DEC-22 — Installer behaviour on a Pest kit without tests.yml (spike S3)

**Question:** What does `laravel new --using` (Herd's flags) change in a kit that already ships Pest, has no `tests.yml`, and keeps CI in `ci.yml` with `matrix.php`?
**Answer:** The installer did not fail on the missing `tests.yml`, but it did two bad things with it. With `--pest`, `installPest()` runs a `str_replace` on `.github/workflows/tests.yml` without checking that the file exists: PHP printed `Warning: file_get_contents(.../.github/workflows/tests.yml): Failed to open stream` (exit code still 0), and the write half of the call then created an empty 0-byte `tests.yml`, which the "Install Pest" commit contains. An empty workflow file is invalid on GitHub Actions. Exit codes of the three runs: `herd-like` (Herd's exact flags: `--database=sqlite --npm --pest --git --boost`) 0, `variant-phpunit` (`--phpunit --no-boost`) 0, `variant-nodb` (no `--database`, `--no-node --no-boost`, no test flag) 0. A first `herd-like` attempt exited 1 for a reason unrelated to the kit rules above: the installer appends ` --no-ansi` (and ` --quiet` with `-q`) to every command it runs when output is not decorated, including each `extra.laravel.installer.post-create-project` command, so my probe hook `@php -r "..."` failed with `Error in argument 3, char 2: no argument for option -`; the probe hook now ends in ` --` so the appended flag is treated as a script argument, and all results below come from the corrected probe. Hook files: `hook-post-create-project-cmd.txt` (written by the kit's Composer `post-create-project-cmd` script) contains `1` in all three runs, because the installer sets `LARAVEL_INSTALLER_DEFER_HOOKS=1` for the create-project phase; `hook-installer.txt` (written by the `extra.laravel.installer.post-create-project` hook, which the installer runs after create-project completes) contains `unset` in all three runs, so the deferral variable is NOT set when installer hooks run. The Pest step (`herd-like` only; with `--phpunit` or no test flag the kit's `composer.json`, `tests/` and workflows are left exactly as shipped, with `pestphp/pest-plugin-drift` still in require-dev): runs `composer remove phpunit/phpunit --dev --no-update`, `composer require pestphp/pest pestphp/pest-plugin-laravel --dev`, `composer update`, `pest --init`, then `composer require pestphp/pest-plugin-drift --dev`, `pest --drift`, `composer remove pestphp/pest-plugin-drift --dev`, then Pint on `tests` and the commit "Install Pest". Net changes: `pestphp/pest-plugin-drift` removed from require-dev (`pestphp/pest` `^5.3` and `pestphp/pest-plugin-laravel` `^5.0` constraints unchanged), all 11 class-based test files under `tests/` rewritten to Pest functions by Drift (the official kit ships class-based PHPUnit tests), `tests/Pest.php` and `phpunit.xml` byte-identical to the kit, plus the empty `tests.yml`. `herd-like.diff` is 1239 lines: 3 hunks of composer.json, 12 test files, `bootstrap/cache/*.php` and `storage/framework/views` (runtime noise), and new files from Boost (`.agents`, `.claude`, `.codex`, `.junie`, `.pi`, `.mcp.json`, `AGENTS.md`, `boost.json`; all but `.codex/config.toml` are already ignored by the kit's `.gitignore`). `composer.json` also gained `laravel/boost` `^2.2` in require-dev (Boost step) and the file lost its trailing newline. `ci.yml` is byte-identical to the kit, so `php-version: ${{ matrix.php }}` (line 12) survived untouched: yes. `configureWorkflowPhpVersion()` only edits `tests.yml` and only the quoted literal pattern `php-version: '8.4'`. `boost:update` entries in `post-update-cmd`: 1 (`@php artisan boost:update --ansi`, appended after the kit's own `vendor:publish` entry; none with `--no-boost`). The installer made its own fresh git repository (4 commits: "Set up a fresh Laravel app", "Install Pest", "Install Laravel Boost", "Configure Boost post-update script"); the kit's `.git` history is not carried over; `--git` was absent in the two variants and they have no `.git`. `variant-nodb` has `database/database.sqlite` and all migrations applied (`users`, `sessions`, `passkeys`, `jobs`, `cache` and so on, 118784 bytes), but the cause is the kit's own `post-create-project-cmd` script (`touch` of the file plus `artisan migrate`): the installer itself deliberately skips migrating for any starter kit and forces `--database` to `sqlite`, and `.env` has `DB_CONNECTION=sqlite` and `APP_URL=http://localhost:8000` in all three.
**Evidence:** `$SCRATCH/herd-like.diff` (summarised; `$SCRATCH` is the spike scratchpad `skv3-spikes`), the three installer logs, the hook files and the decompiled `NewCommand.php` of Laravel Installer 5.31.1 (Herd phar), PHP 8.4.23, Composer 2.10.2, 2026-10-10.
**Consequence:** Kit rules for M1 Task 6 and Task 13: (1) The kit must ship a valid `.github/workflows/tests.yml`; without it the `--pest` run prints a PHP warning and commits an empty, invalid workflow. The cleanest form is a real workflow that already runs Pest and does not contain the string `./vendor/bin/phpunit`; if it contains a quoted literal `php-version: 'X.Y'` the installer rewrites it to the PHP version of the machine running `laravel new` (8.4), so use `php-version: ${{ matrix.php }}` there as in `ci.yml`, which is never touched. (2) `ci.yml` with `matrix.php` can stay as is. (3) Ship `tests/Pest.php` with `->use(RefreshDatabase::class)` already active (not commented out) and Pest-function tests without a `uses(RefreshDatabase::class);` line, and keep `pestphp/pest-plugin-drift` out of `require-dev`, so every Pest-step edit (comment swap, `uses` removal, Drift conversion, drift removal) is a no-op. Drift on already-converted tests was not run in this spike. (4) Do not put `boost:update` in the kit's `post-update-cmd`: the installer adds exactly one entry with `--boost`, so a kit entry would duplicate it. (5) `laravel/boost` must not be in the kit's `require-dev` for the same reason. (6) Any `extra.laravel.installer.post-create-project` command must tolerate a trailing `--no-ansi` or `--quiet`: Artisan commands do, `php -r` needs a trailing ` --`, and a kit hook cannot rely on `LARAVEL_INSTALLER_DEFER_HOOKS` (it is set only for the Composer `post-create-project-cmd` phase, not for installer hooks). (7) `skv:bootstrap` (or the kit's `post-create-project-cmd`) must create `database/database.sqlite` and migrate, because the installer never does either for a starter kit, with or without `--database`. (8) The kit must expect that the installer rewrites `composer.json` (formatting, no trailing newline), commits to a new git history, and generates Boost files (`.agents`, `.claude`, `.codex`, `.junie`, `.pi`, `.mcp.json`, `AGENTS.md`, `boost.json`) that the kit's `.gitignore` already covers except `.codex/config.toml`.
