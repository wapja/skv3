# skv3 — Design Spec

- **Date:** 2026-10-10 (rev. 2, after multi-lens review)
- **Status:** Draft, awaiting owner review
- **Predecessor:** `~/Herd/skv2` (spec `docs/superpowers/specs/2026-07-19-skv2-spec.md`, decisions D1–D34 in its README)
- **Package:** `frankcornet/skv3` (`"type": "project"`, MIT, public GitHub + Packagist)

## 1. Goal

skv3 is an opinionated, multi-tenant Laravel starter kit. It keeps **all** functionality of skv2 and is more modern, more user-friendly and much easier to set up. The headline experience:

> Herd → *New site* → *Custom Starter Kit* `frankcornet/skv3` → *Open site* → a browser setup wizard (at most 5 questions, pre-filled) → a working, seeded app. Under 5 minutes, no file edits, no terminal needed on the default answers.

The same setup is available as `php artisan skv:install` for terminal users, CI and AI agents.

### 1.1 Non-goals (v1)

- Multi-database tenancy, per-organisation custom domains, Postgres row-level security.
- Path-based tenant identification (the resolver sits behind an interface so it can be added later).
- Billing (Cashier/Spark/Paddle), Filament, a Laravel MCP app server, an in-app `/docs` route.
- Switching to stancl/tenancy or spatie/laravel-multitenancy.
- Languages beyond `nl` and `en` (the language list is config-driven).
- Telescope (replaced by Debugbar + Pail + Herd Dumps/Log Viewer).
- Membership of more than one organisation per user.
- Self-service account deletion (skv2 D33 carried over).

## 4. Feature inventory (parity checklist)

Every item must exist in skv3 and be covered by at least one test (traceability: each test file starts with a `covers §4.x` docblock line; a script lists §4 bullets without a test reference). "→" marks a change from skv2.

### 4.0 App defaults
- `AppServiceProvider::configureDefaults()`: `Date::use(CarbonImmutable::class)`; `DB::prohibitDestructiveCommands(app()->isProduction())`; strong `Password::defaults()` in production; `Model::shouldBeStrict(! app()->isProduction())` (enabled by the end of M2 at the latest, with scoped exceptions per §13).
- Tests: `now()` is `CarbonImmutable`; `migrate:fresh` / `db:wipe` refused in production.

### 4.1 Multi-tenancy
- Single database; organisation resolved from the subdomain: `{slug}.{apex}` = tenant host, `{apex}` and `admin.{apex}` = central hosts.
- → Env: `TENANCY_APEX_DOMAIN` (default: `APP_URL` host), `TENANCY_ADMIN_SUBDOMAIN` (default `admin`).
- Resolver binds the current organisation, sets the Spatie team id, clears state on central hosts. Unknown or soft-deleted slugs → friendly tenant 404 with a link to the apex.
- Global organisation scope + `BelongsToOrganisation` trait (auto-fill `organisation_id`, `organisation()` relation).
- Unscoped auth user provider for sessions, password broker, 2FA and passkey lookups.
- Membership middleware: logs out inactive users / users on the wrong host. → With a flash message explaining why; impersonation ends cleanly (with `impersonation.stop` logged) instead of logging the impersonator out.
- Tenant URL helper keeping scheme **and port** (§6.2).
- Config: apex domain, admin subdomain, tenant models list (soft-delete cascade), reserved slugs.
- Soft-deleting an organisation soft-deletes its tenant models with the same timestamp; restore restores only those rows; force delete does not cascade (purge is explicit, §4.3).
- Host-only session cookies (`SESSION_DOMAIN=null`) → per-subdomain sessions.
- Tenant name in the brand on tenant hosts.

### 4.2 Authentication (Fortify)
- Login scoped per host: an active user that belongs to the current host; super admins log in on any host. 2FA and passkey login use the same rule.
- Registration and email verification disabled; invite-only.
- Password reset. → The reset URL points at the user's own host (`ResetPassword::createUrlUsing` + `tenant_url()`); neutral status message whether or not the address exists; `password.email` throttled; tests run on tenant hosts.
- TOTP 2FA: enable/confirm/disable with QR + setup key, password confirmation, recovery codes (show/hide/regenerate). → Copy, download, confirm-before-regenerate.
- Passkeys (module, §6.8): register/list/delete, login from the login page, `.well-known/passkey-endpoints`. → The RP id is **always the apex** (`passkeys.relying_party_id`, override `PASSKEYS_RELYING_PARTY_ID`), a valid registrable suffix for the apex, `admin.{apex}` and every `{slug}.{apex}`. It never changes per request, so one passkey works on every host the user may log in on and survives a slug rename. Only `passkeys.allowed_origins` changes per request: set to the current request origin (scheme + host + port) on `TenantResolved` / central resolution, reset on `TenantForgotten`. These are the `passkeys.*` keys the package reads at request time — not `fortify.passkeys.*` (skv2's no-op). Login is authorised by `Passkeys::authorizeLoginUsing()` with the host rule above; passkey users load through `Passkeys::useUserModel()` with an unscoped user model (skv2 returned null → 500 for super admins).
- Password confirmation flow.
- Rate limiters for login (email+IP, IP), two-factor, passkeys. → Count only failed attempts.
- Lower-cased emails.
- `Illuminate\Session\Middleware\AuthenticateSession` on every authenticated route (needed for §6.6 sessions).

### 4.3 Organisations
- Model: name (unique), slug (unique), description, soft deletes. → `require_second_factor` (bool, default false, §6.6).
- Index (tenant host shows only its own), create, edit, soft delete.
- → Archived view with restore and purge. `restore` = `organisations.delete`. **Purge** (force delete) is only available for archived organisations, gated by a `forceDelete` policy ability mapped to `organisations.delete`, requires typing the slug, and runs a `PurgeOrganisation` action in one transaction, deleting in order: invitations, users including trashed ones (passkeys and sessions cascade; avatar files deleted after commit), team roles and the `model_has_roles` / `model_has_permissions` rows for its team id, then the organisation. Activity rows are kept (`activity_log.organisation_id` has no FK). Logs `organisation.purged`. `users.organisation_id` keeps `restrictOnDelete` as a safety net.
- Policy: view/update = permission + ownership; create/delete/restore/forceDelete = super admin.
- Slug rename redirects to the new subdomain (via the handoff token, §6.4).
- `organisation_admin` role available for every organisation (mechanism per spike S2, §6.3).
- Super-admin tenant picker. → Merged into the organisations index ("Open" action using the handoff token).
- → Slug rule: `[a-z0-9-]`, 3–63 chars, no leading/trailing hyphen, not in `config('tenancy.reserved_slugs')` (default: `admin`, `www`, `api`, `app`, `mail`, `smtp`, `ftp`, `static`, `assets`, `cdn`, `docs`, `help`, `status`, `support`, `dashboard`, `login`, `test`).
- → Organisation wizard: name, slug (auto, live availability, `slug.apex` preview), first admin's email → creates the organisation and sends the invitation.

### 4.4 Users
- Soft deletes, status enum (`pending_activation`, `active`, `disabled`), per-user locale, audit logging of fillable fields except password.
- Super admin. → Explicit `is_super_admin` boolean, the only source of truth (§6.3).
- Index: search, status filter, role filter, 25 per page, organisation column and roles on the admin host, delete modal, impersonate action (tenant host, module on). → Search is case-insensitive on both drivers via `whereLike(..., caseSensitive: false)`; no raw `ilike`/`like`. → Archived view with restore: `restore` = `users.delete` + same organisation; refused while the organisation is archived or when the email is now taken by a non-deleted user.
- Edit page doubles as show page: name, email, status, roles (`roles.assign`). → `pending_activation` cannot be set by hand; email uniqueness uses `withoutTrashed()` everywhere.
- Policy: view, update, delete (not yourself), impersonation matrix.
- Factory states: pending, disabled, superAdmin, withTwoFactor, unverified.
- Email unique among non-deleted users: the users migration creates `email` without a unique constraint, then one `CREATE UNIQUE INDEX users_email_unique ON users (email) WHERE deleted_at IS NULL` (valid on Postgres and SQLite). No `ALTER TABLE … DROP CONSTRAINT`.
- → Avatar upload (§6.6). → `users.appearance` (DEC-12).

### 4.5 Invitations
- Invite by email with locale and roles; user created as pending. → At least one role required.
- Invitation: token, `expires_at` (configurable, default 7 days), `reminder_sent_at`, `accepted_at`, inviter.
- → Accept URL built in one place: `Invitation::acceptUrl()` = `tenant_url($org, URL::temporarySignedRoute('invitations.accept', $expires_at->addDays(config('skv.invitations.signature_grace_days', 30)), ['token' => $token], absolute: false))`; the route uses `signed:relative` so it survives http↔https and host rewrites between queueing and clicking. **Two-layer expiry:** `expires_at` (domain expiry) is checked in the accept component and renders the "expired" page with the resend button; the signature lives longer so only links older than the grace period get a 403. Never sign with `expires_at` itself.
- Actions: invite, accept, remind, cancel (cancel hard-deletes the invitation and soft-deletes the pending user). → Team-id switching via `withPermissionsTeam()` (`finally`).
- Markdown mails: invitation, reminder. → Queued (`ShouldQueue`), `afterCommit`.
- Pending list: inviter, relative expiry, remind (`users.invite.resend`), cancel (`users.delete`). → Crash-proof with a deleted inviter (`withTrashed`, null-safe). → Remind refused for accepted invitations.
- Accept page: set password; expired state; resend button for authorised users. → Invitee chooses their own name; logged in after accepting; separate "already accepted — please log in" state.
- Audit events: sent, reminder sent, accepted, cancelled.
- Re-inviting an address after cancel works.
- → The `invitations` table is the single source of truth (no `users.activation_*` columns).
- → "Copy invite link" button. → Super admins can invite from the admin host by picking an organisation.
- → Bulk invite (§6.6). → Generic "this address can't be invited" message (no cross-organisation enumeration).

### 4.6 Roles and permissions (spatie/laravel-permission, teams mode)
- 15 permissions: `users.view/create/update/delete/invite.resend/impersonate`, `roles.view/assign/manage`, `organisations.view/create/update/delete`, `activity_log.view`, `system.health`.
- Super-only: `roles.manage`, `organisations.create`, `organisations.delete`, `system.health`.
- Global `super_admin` role (display badge only, §6.3); `organisation_admin` = catalogue minus super-only.
- `Gate::before` grants super admins everything except `impersonate` and the self-destructive abilities, which return `null` so policies and guards always run.
- Roles index with global badge, permission badges, CRUD under `roles.manage`. → **System roles** (`Role` enum: `super_admin`, `organisation_admin`) cannot be renamed, deleted or used as a new role's name; their permissions are read-only in the UI and owned by `permissions:sync`. Custom roles are always team-scoped: created on a tenant host, or on the admin host only after an organisation is explicitly picked; a null-team custom role is never created; custom roles never receive super-only permissions. Role lookups by id are scoped to the current team (fixes W1's cross-team edit).
- Pivot primary keys exclude `team_id` (null team allowed, skv2 D28).
- Route-level `can:` middleware and permission-gated navigation.
- → `Permission` and `Role` backed enums; no permission string literals in app code.
- → Idempotent `permissions:sync` command.
- → Role assignment only via an `UpdateUserRoles` action with full authorisation; roles validated against the target organisation's team; null-team roles rejected except as allowed by the S2 outcome (§6.3) (fixes W1).
- → Guards: last super admin, last organisation admin, removing your own admin role, disabling yourself (fixes W2, W12).

### 4.7 Impersonation (module, §6.8)
- Reason required (non-blank, ≤ 500 chars), `Gate::authorize('impersonate')`, depth 1.
- Matrix: target never a super admin; super admin may impersonate anyone; others only same-organisation non-admins; tenant host only. → Target must be active (fixes W3).
- Audit `impersonation.start` (with reason) / `impersonation.stop`; causer rewritten to the real user, `impersonated_as` recorded.
- Sticky banner with stop button; `DELETE /impersonation`. → "Stopped" toast is shown.

### 4.8 Audit log (spatie/laravel-activitylog v5)
- Custom Activity model: causer rewrite during impersonation; organisation tagging; diffs in `attribute_changes`.
- Authentication subscriber: login, login failed (with email), logout, password reset requested/completed, 2FA enabled/disabled.
- Viewer: date range, action, subject type, causer filters; 50 per page; diff and reason columns; tenant-scoped; cross-scope causer names.
- Dashboard widget: last 10 entries. → Gated by `activity_log.view`; causers resolved without the tenant scope.
- → Real indexed `organisation_id` column (no FK), `created_at` index, IP + user agent captured.
- → `ActivityEvent` enum with translated labels.
- → Also logged: organisation CRUD/purge, role/permission changes, role assignments, security settings (password, passkeys, recovery codes, sessions, second-factor setting).
- → Filters in the URL (`#[Url]`), `resetPage()` on filter change, detail flyout, CSV export (§6.6).
- → Retention: published `config/activitylog.php` sets `clean_after_days => (int) env('ACTIVITYLOG_RETENTION_DAYS', 365)`; `actions.clean_log` points to `App\Actions\Audit\CleanActivityLog`, which runs the delete inside `Tenant::bypass()`.

### 4.9 Ops
- `/up`: framework liveness route (no auth; 200, or 500 on failure). Documented as liveness only.
- `/health-check`: registered outside the web group (`withRouting(then:)`), `throttle` only — no session, cookies, tenant or locale middleware. Authorised only by header `X-Health-Check-Key`, `hash_equals` against `HEALTH_CHECK_KEY`; a blank or missing configured key always → 403. Checks: database, queue (failed jobs; not ok when the table is missing), mail (SMTP probe only when `MAIL_MAILER=smtp`, else info), last backup (skipped when the backups module is off). JSON; 200 when all pass, 503 when any fails; results cached briefly. → skv2's `system.health` permission path (D10) moves to the System page (§6.5), which shows the same cached results.
- Backups (module, §6.8): database only, encrypted, monitored. → Off on SQLite; last-backup time read via the backup destination API; `BACKUP_ARCHIVE_PASSWORD`, `BACKUP_NOTIFY_EMAIL` in `.env.example`; failure-only notifications; `pg_dump` auto-detected (`PG_DUMP_BINARY_PATH`).
- Scheduler (with `onOneServer()` + `withoutOverlapping()`): `backup:clean` 01:30 and `backup:run --only-db` 02:00 (module on), `backup:monitor`, `queue:prune-failed`, `auth:clear-resets`, `activitylog:clean --force` (the command uses `ConfirmableTrait` and cancels itself in production without `--force`). `model:prune` only once a model is prunable.
- Custom error pages 403/404/419/429/500/503. → Self-contained (§6.5).

### 4.10 UI shell and settings
- Sidebar layout with permission-gated navigation, mobile header, user menu, toasts.
- Settings: profile (name, email, language), appearance (light/dark/system), security (password, 2FA, passkeys).
- → No self-service account deletion (D33): M1 removes the starter kit's delete-user form, component, view and include. Test: the profile page renders no delete-account control and no route or action deletes `auth()->user()` outside the admin users flow.
- Dashboard: for every signed-in user, an Organisation card (current organisation; "Platform" on central hosts) and a "Your roles" card with translated role badges ("No roles assigned" when empty).
- → Everything else in §6.5.

### 4.11 Localisation
- `nl` default, `en` fallback; per-user locale middleware.
- → Guests get a locale from `Accept-Language` (changes skv2 D17); see §6.5.

### 4.12 Seeding
- Permission catalogue + `super_admin` always seeded (essentials seeder, idempotent).
- Demo data: super admin, organisations `demo1` and `demo2`, each with an admin and a user. → Split into an essentials seeder (always) and a demo seeder (optional, refuses to run in production); emails derived from the apex; demo users share the password `password`, printed in the setup summary. → `skv:create-super-admin` and `skv:create-organisation` commands.

## 5. Setup and distribution

### 5.1 Entry points

1. **Herd wizard**: *New site* → *Custom Starter Kit* → `frankcornet/skv3`, or the deep link `https://herd.laravel.com/new/frankcornet/skv3`.
2. **Terminal**: `laravel new myapp --using=frankcornet/skv3` (with or without `--database`).
3. **Composer**: `composer create-project frankcornet/skv3 myapp`.
4. **Clone/template**: `git clone …` → `composer setup`.

All four end in the same phase 2 (§5.3).

### 5.2 Phase 1 — create (non-interactive)

Installer facts this design relies on (installer 5.31.1 and 5.32.0, Herd 1.30.2):
- Herd's GUI runs `laravel new <name> --no-interaction --no-ansi --database=sqlite --npm …` plus its checkbox flags (testing framework, git, Boost). There is no TTY; prompts take their defaults.
- The installer runs `composer create-project <kit> <dir> --stability=dev` (no version) with `LARAVEL_INSTALLER_DEFER_HOOKS=1`. With `--stability=dev`, Composer installs the **default branch** (`dev-main`), not the latest tag (DEC-18).
- Then: `post-root-package-install` again, `key:generate`, the kit's `extra.laravel.installer.post-create-project` commands, a rewrite of every literal `php-version: 'x.y'` in `.github/workflows/tests.yml`, the `APP_URL` rewrite (`http://<name>.test` when parked and resolvable, else `http://localhost[:8000]`), and the `DB_*` rewrite + `migrate` **only when `--database` is passed** (otherwise the kit is expected to migrate itself).
- Herd Pro mail rewrite (`MAIL_MAILER=smtp`, Herd's SMTP port, `MAIL_USERNAME`), optional `git init` + commit (after the kit hooks), optional Pest (`composer remove phpunit` → `composer require pest…` → full `composer update` → `pest --init` → drift round trip → edits `tests.yml` and `tests/Pest.php`), npm install + build (failure ignored), optional Boost (`composer require "laravel/boost:^2.2" -W`, `boost:install`, appends `boost:update` to `post-update-cmd` without a duplicate check).
- The kit's hooks run **before** the DB rewrite, migrate and `git init`.

Kit rules that follow:
- **Composer hooks:**
  - `post-root-package-install`: `@php -r "file_exists('.env') || copy('.env.example', '.env');"`
  - `post-create-project-cmd`: `@php artisan skv:bootstrap --no-interaction --ansi`
  - `extra.laravel.installer.post-create-project`: `@php artisan skv:bootstrap --no-interaction`
- **`skv:bootstrap`** returns early when `LARAVEL_INSTALLER_DEFER_HOOKS` is set. Otherwise it is idempotent and does exactly: (1) copy `.env.example` → `.env` if missing; (2) generate `APP_KEY` if empty; (3) if `APP_URL` is `http://localhost[:8000]` and Herd is present, rewrite it to `http://<folder>.<herd tld>` (mirrors the installer's `generateAppUrl`); (4) if `DB_CONNECTION=sqlite`, touch `database/database.sqlite` and run `migrate --graceful --force`; (5) create the one-time setup token (§5.3.4); (6) print "Open <APP_URL>/welcome-setup". It never chooses a database, never prompts, never caches config/routes, and respects `LARAVEL_INSTALLER_NO_NODE`. In the Herd route the installer's later `migrate` is a no-op.
- **`.env.example`** keeps Laravel's default lines so the installer's replacements match: `APP_URL=http://localhost`, `DB_CONNECTION=sqlite`, commented `# DB_HOST=127.0.0.1` … `# DB_PASSWORD=`, `MAIL_MAILER=log`, `MAIL_PORT=2525`, `MAIL_USERNAME=null`. It also ships `SESSION_DRIVER=database`, `SESSION_COOKIE=app_session` (fixed and neutral, §5.3.3), `HEALTH_CHECK_KEY=`, `TENANCY_APEX_DOMAIN=`, `MODULE_PASSKEYS=true`, `MODULE_BACKUPS=true`, `MODULE_IMPERSONATION=true`, `ACTIVITYLOG_RETENTION_DAYS=365`, `BACKUP_ARCHIVE_PASSWORD=`, `BACKUP_NOTIFY_EMAIL=`.
- **Workflows:** the kit's CI lives in `.github/workflows/ci.yml` and sets PHP via `matrix.php`, never as a quoted literal, so the installer's regex never matches. The kit ships no `tests.yml`.
- **Pest:** the kit already uses Pest; the installer's Pest step may re-resolve dependencies (`composer update`), so the kit's constraints are the real tested minimums. Spike S3 records the full diff the installer produces and the kit adjusts shipped files so the edits are no-ops.
- **Boost:** the kit's `composer.json` does not list `boost:update` in `post-update-cmd`; `skv:install` adds it once, and restores the `laravel/boost` constraint to `^2.10` if the installer lowered it.
- **Flux Pro:** never shipped and never referenced in the kit's `composer.json`/`composer.lock` (§6.7).

### 5.3 Phase 2 — set up (browser wizard or CLI)

#### 5.3.1 Setup steps

Steps live in `app/Setup/Steps/*`:

```php
interface SetupStep
{
    public function key(): string;            // stable id: progress tracking, state file, marker, UI
    public function label(): string;          // translated, user-facing
    public function isComplete(SetupContext $context): bool; // idempotency check
    public function isLong(): bool;           // runs detached in the browser (§5.3.3)
    public function run(SetupContext $context): StepResult;  // done | skipped | manual(command, reason)
}
```

A step that cannot run from the current context returns `StepResult::manual($command, $reason)`: the browser shows the command with a copy button and a "Re-check" button; the CLI prints it.

#### 5.3.2 Detection, questions and the `--answers` schema

**Detection** runs before questions are shown or `--answers` is validated: Herd present; Herd Pro and its mail service (`~/Library/Application Support/Herd/config/herd.json`: `mails`, `smtpPort`; services via `herd services:list --json`, never trusting exit codes); a reachable Postgres (try Herd's known credentials); Flux Pro installed; `claude` on PATH; current host and scheme (browser) or folder + `herd tld` (CLI).

**Questions** — this table is also the `--answers` JSON schema (`tests/Fixtures/e2e-answers.json` exercises it). The browser shows the defaults pre-filled; `skv:install --no-interaction` uses them as-is.

| Key | Type | Default |
|---|---|---|
| `app_name` | string | `Str::headline(basename(base_path()))` |
| `database` | `pgsql` \| `sqlite` | `pgsql` if a reachable Postgres was detected, else `sqlite` |
| `start_with` | `demo` \| `super_admin` | `demo`. With `super_admin`, `super_admin_email` + `super_admin_password` are required; with `--no-interaction` and either missing, the command fails before any step runs |
| `modules` | subset of `passkeys`, `backups`, `impersonation` | all three; `backups` removed on sqlite |
| `https` | bool | true; forced true while `passkeys` is on |
| `playwright` | bool | false |
| `claude` | bool | true if `claude` is on PATH, else false |

#### 5.3.3 Steps (in order)

1. **Environment file**: write `.env` atomically (temp file + rename): `APP_NAME`; `APP_URL` and `TENANCY_APEX_DOMAIN` from the browser request host (or folder + Herd TLD in the CLI); a random 40-char `HEALTH_CHECK_KEY` if empty; `APP_FAKER_LOCALE=nl_NL`; module flags `MODULE_*`; mail: when Herd Pro mail is active, `MAIL_MAILER=smtp`, `MAIL_HOST=127.0.0.1`, `MAIL_PORT=<smtpPort>`, `MAIL_USERNAME="${APP_NAME}"` unless the installer already set non-default values — otherwise keep `MAIL_MAILER=log` and say so in the summary. Existing `APP_KEY` preserved. `DB_*` is **not** written here. `APP_URL` stays http until the HTTPS step.
2. **Database (atomic switch)**: for `pgsql`, create the app database and `<db>_test` over PDO, configure the connection at runtime (`config([...])` + `DB::purge()`), migrate, `permissions:sync`, run the essentials seeder, then the demo seeder or `SetSuperAdmin` for the real super admin — and only after all of that succeeds, write `DB_*` to `.env`. For `sqlite`, migrate (if needed), sync and seed on the existing file. Writes `.env.testing` (`<db>_test`, or in-memory SQLite). Verifies that no `database/schema/pgsql-schema.*` dump is present (§7.3).
3. **`herd.yml`**: name, `php: 8.4`, `secured: <https answer>`, PostgreSQL 18 service when `pgsql`.
4. **Branding**: `APP_NAME` and accent into `.env`-backed `config/branding.php` values.
5. **Frontend** (long): if Node satisfies `^20.19 || >=22.12` and the manifest is missing or stale, `npm ci && npm run build`; optional `npx playwright install chromium`. On failure: `manual('npm ci && npm run build', reason)`.
6. **Git**: `git init` if there is no repository; `git config core.hooksPath .githooks`.
7. **Claude** (when chosen; long): `boost:install --no-interaction` (needs a `.test` `APP_URL`); generate `.mcp.json` with Boost + Herd MCP; `claude plugin install superpowers --scope project` if `claude` is on PATH; add `boost:update` to `post-update-cmd` once.
8. **Doctor**: run `skv:doctor` (§5.4).
9. **Marker**: write `storage/app/skv-installed` (JSON: kit version, answers without secrets, `start_with`, timestamp, summary). Delete `storage/app/private/skv-setup-token` and `storage/app/private/skv-setup.json`.
10. **Herd site** (last): (a) parked = the parent of `base_path()` is in `herd paths` (JSON); if not parked and not in `herd links`, `herd link <name>` (no `--update-env`/`--secure`/`--isolate`; `link` also runs `boost:update` when Boost exists, which is acceptable at this point); (b) when HTTPS is on: `herd secure <name>`, then rewrite `APP_URL`/apex to https in `.env` in-process (`herd secure` has no `--update-env`); (c) `herd isolate 8.4 --site=<name>` only when the site would be served by PHP < 8.4 and is not isolated — in the browser this is always `manual(...)` because isolate restarts php-fpm.
11. **Summary**: clickable URLs (apex, admin host, demo tenants), logins (demo: emails + `password`) or "log in as <email>", next steps, any `manual()` commands left.

`composer setup` = `["Composer\\Config::disableProcessTimeout", "composer install", "@php -r \"file_exists('.env') || copy('.env.example', '.env');\"", "@php artisan skv:bootstrap --no-interaction", "@php artisan skv:install"]`. `skv:install` also runs the bootstrap logic as an implicit step 0, so a bare `php artisan skv:install` on a clone works.

#### 5.3.4 Browser wizard runtime

- **Route**: `/welcome-setup` and its Livewire update endpoint are registered (local environment only) **without a domain constraint**, outside the tenant resolver, membership middleware and second-factor enforcement. While the marker is absent, the resolver skips resolution for every host instead of returning the tenant 404, and `/` redirects to the wizard (see access gate).
- **Access gate** (all must hold, else 404): `app()->isLocal()`; marker absent; no `X-Forwarded-For` / `X-Forwarded-Host` / `X-Original-Host` / `X-Expose-*` header; a valid one-time setup token. `skv:bootstrap` writes a 32-byte token to `storage/app/private/skv-setup-token`. A request to `/` that passes the other conditions **and** finds no user with `is_super_admin = true` is redirected to `/welcome-setup?token=…`; the wizard checks the token with `hash_equals` and stores it in its (file) session. Later wizard requests are authorised by that session token, so step 2 seeding a super admin does not lock the wizard out; the token file is deleted in step 9. The request IP is **not** a gate: under Herd every request arrives from 127.0.0.1, including `herd share` traffic. TrustProxies stays at its default. Spike S6 confirms which headers `herd share` adds.
- **Runtime state**: a dedicated `setup` middleware group sets `session.driver=file`, `cache.default=file` and `queue.default=sync` before `StartSession` runs, so the wizard never depends on the database that changes under it. Answers and per-step status live in `storage/app/private/skv-setup.json` (the super-admin password is hashed on entry; only the hash is stored), so a reload or 419 resumes at the first incomplete step. `SESSION_COOKIE` is fixed in `.env.example`, so writing `APP_NAME` never renames the session cookie.
- **Execution**: the wizard never uses the queue. Each step is one Livewire action call with `set_time_limit` raised; every step that touches the DB purges and reconnects so it uses the latest values. Steps with `isLong()` (frontend, Playwright, Claude) are started as a detached process (`Process::start` with `nohup`/`setsid`) writing exit code and output tail to `storage/app/private/skv-setup/{step}.json`; the page polls (`wire:poll.2s`) until it finishes (Herd's nginx has a 60 s FastCGI timeout).
- **Herd step**: because `herd secure`/`isolate` restart nginx and php-fpm and the secured vhost 301-redirects http to https, step 10 runs after the marker, as a detached process logging to `storage/logs/skv-herd.log`. The page then stops making Livewire requests, polls the https origin of `/up` (`fetch(..., {mode: 'no-cors'})`), and does a full-page navigation to a single-use signed login URL for the new super admin (or the login page for demo) on the final origin. The summary is read from the marker. If the detached process cannot start or the poll times out after 60 s, step 10 returns `manual('herd secure <name>')`, `APP_URL` stays http, and — when the user continues without securing — the passkeys module is switched off (`MODULE_PASSKEYS=false`) with a summary note on how to enable it later.
- **No Vite dependency**: the setup layout (`layouts/setup`) does not use `@vite`. It inlines a prebuilt, committed `resources/setup/setup.css` (Tailwind + Flux styles generated from the setup views; `npm run build:setup` regenerates it; CI checks it is current) and uses `@fluxAppearance`, `@fluxScripts` and `@livewireScripts`, which are served through PHP routes. The wizard renders with `public/build` absent.

**CLI**: `php artisan skv:install [--answers=JSON] [--no-interaction] [--force]` uses the same steps with Laravel Prompts (`form()`, `task()`), in the order above (the Herd step runs normally outside php-fpm).

**Spike S1 dependency**: whether a php-fpm request under Herd can run `herd`, `npm`, `git` and `claude`, and whether a detached process outlives the request and the nginx/php-fpm restart. Fallback: those steps return `manual(command)`; env, DB, seed, config and marker steps run in-process regardless.

### 5.4 Doctor

`php artisan skv:doctor [--fix] [--json]`. Each check returns `pass`, `warn`, `fail` or `skipped` with a message and the exact fix command. A check decides whether it applies from detection and the marker answers, and returns `skipped` otherwise. **Green = no `fail`.** `--fix` performs only safe repairs (`permissions:sync`, flag/role drift, `storage:link`, `core.hooksPath`, asset build).

Checks (conditions in brackets):
- PHP ≥ 8.4; `ext-gd` present; `APP_KEY` set.
- Herd present (warn when absent); Herd Pro (warn when absent).
- Site served by Herd (parked under a `herd paths` entry or in `herd links`); [HTTPS on] listed in `herd secured`.
- Wildcard subdomain resolves (`probe.{apex}`); without Herd the fix text prints the `/etc/hosts` lines for the apex, `admin.` and every organisation slug.
- Apex matches `APP_URL`.
- DB reachable; migrations current; [pgsql] test DB present; warn when a `database/schema/pgsql-schema.*` dump exists and `psql`/`pg_dump` cannot be resolved.
- Permissions in sync; organisation admin role(s) present per §6.3; at least one active super admin; `is_super_admin` ↔ `super_admin` role drift.
- `SESSION_DRIVER=database`; `AuthenticateSession` registered.
- `HEALTH_CHECK_KEY` set.
- Node satisfies `^20.19 || >=22.12`; Vite manifest present and current.
- [`MAIL_MAILER=smtp`] the configured `MAIL_PORT` is listening; [log] info line.
- [backups on] `pg_dump` found (auto-detect `/Users/Shared/Herd/services/postgresql/*/bin`).
- [Flux Pro installed] credentials present.
- Queue connection works.
- Git hooks path set; [playwright] Playwright installed (warn).
- [claude] `CLAUDE.md` imports `@AGENTS.md` and `AGENTS.md` exists; MCP servers configured; superpowers installed (warn).
- Setup token file absent once the marker exists (warn).

The same check classes back the System page (§6.5) and the `/health-check` checks.

## 6. Architecture

### 6.1 Directory conventions

- `app/Tenancy/` — tenancy core (§6.2).
- `app/Authorization/` — `Permission`, `Role` enums, catalogue, `permissions:sync`, `withPermissionsTeam()`, `SetSuperAdmin`.
- `app/Actions/{Audit,Invitations,Users,Organisations,Settings}/` — single-purpose action classes; Livewire components call actions, never contain domain logic.
- `app/Setup/` — steps, context, state file, wizard support, doctor checks.
- `app/Support/` — small helpers (URL, branding, locale, `Skv` facade incl. `hasFluxPro()`).
- `resources/views/pages/**` — full-page Livewire multi-file components (`pages::` namespace, the official kit's convention); `resources/views/components/**` — reusable Livewire/Blade components (DEC-05). `config/livewire.php` sets `make_command => ['type' => 'mfc', 'emoji' => false]`; existing components are converted with `livewire:convert --mfc` and their `⚡` directory names renamed (the command keeps the emoji of the source name).
- `config/skv.php` (module flags read from `MODULE_*` env, invitation and second-factor settings), `config/tenancy.php`, `config/branding.php`.

### 6.2 Tenancy core

- `CurrentTenant` scoped singleton; `Tenant` facade: `current(): ?Organisation`, `check(): bool`, `run(Organisation $org, Closure $fn)`, `bypass(Closure $fn)`, `forget()`.
- Events `TenantResolved` / `TenantForgotten`; listeners set/reset the Spatie team id and `passkeys.allowed_origins` (the RP id stays the apex, §4.2).
- `TenantResolver` interface with a `SubdomainResolver`; slug lookup cached, invalidated by the organisation observer. Reserved slugs and the admin subdomain are never resolved as tenants.
- **Host scoping**: `Route::tenant(fn)` and `Route::central(fn)` are route groups that attach `EnsureTenantHost` / `EnsureCentralHost` middleware — they do **not** use `Route::domain()`, so route names, `route()` calls and `mount()` signatures carry no `{tenant}` parameter. Both middleware are registered with `Livewire::addPersistentMiddleware()` and placed before `can:` in the middleware priority. Only single-host routes go in these groups; shared routes keep one name. Component actions that need a particular host keep an explicit guard (`Tenant::check()` / `#[RequiresTenant]`), each covered by a forged `/livewire/update` test from the wrong host.
- **Route × host matrix** (normative for M2–M5):

| Route | Host | Notes |
|---|---|---|
| `/` | any | guest → login; tenant host → dashboard; super admin on central → organisations index; before setup → wizard (§5.3.4) |
| `dashboard`, `users.index`, `users.edit`, `invitations.pending`, `roles.index`, `organisations.index`, `organisations.edit`, `activity.index`, `settings.*`, `system.index` | any | on central hosts only super admins pass (membership middleware); central views run queries in `Tenant::bypass()` and show an organisation column/filter |
| `users.invite`, `invitations.bulk` | any | on central an organisation picker is required |
| role create | tenant, or central with an explicitly picked organisation | |
| impersonation start | tenant | module on |
| `impersonation.stop` | any | module on |
| `invitations.accept` | the invitation's tenant host | `signed:relative` |
| `/auth/handoff/{token}` | any | bound to target host |
| Fortify / passkey routes, `.well-known/passkey-endpoints` | any | host-scoped login rule |
| `/up`, `/health-check` | any | stateless |
| `/welcome-setup` | any | local, before setup only |

  A Pest dataset test covers every named route × {tenant, apex, admin} × {guest, member, org admin, super admin} with the expected status or redirect.
- **Strict mode** (`config('tenancy.strict')`): querying a tenant model with no tenant bound throws `TenantNotResolvedException`. It applies to HTTP and Livewire requests and to queued jobs that carry a `tenant_id`. Artisan commands, scheduled tasks, seeders, migrations, setup steps, doctor checks and `/health-check` run in central (bypass) context by default (via a `CommandStarting` listener and explicit wrapping); commands that work per organisation iterate with `Tenant::run()`. On central hosts, reads of tenant models must use `Tenant::bypass()` explicitly; the unscoped auth user provider is exempt by design; the cascade runs in bypass. An arch test limits `Tenant::bypass()` to `App\Console`, `App\Setup`, `App\Tenancy`, `App\Actions\Audit`, `Database\Seeders`, the central Livewire components and the health controller.
- **Queue tenant context**: `Queue::createPayloadUsing(fn () => ['tenant_id' => Tenant::current()?->id])` adds the tenant to every payload (jobs, queued mailables, notifications, listeners). A `JobProcessing` listener binds it before the command is unserialized (so model restore and `loadMissing()` already run under the right tenant); a missing or soft-deleted organisation fails the job without retry. `JobProcessed` / `JobFailed` / `JobExceptionOccurred` call `Tenant::forget()`. A payload without `tenant_id` runs centrally.
- `tenant_url(Organisation|string $slug, string $path = '/')` takes scheme and port from the current request, or from `APP_URL` / the apex in workers and the console. Signed accept URLs are built with it and tested from a worker context.
- Soft-delete cascade over `config('tenancy.tenant_models')` (includes `Activity`); an arch test asserts every model with `organisation_id` uses the trait and is listed. Activity rows with `organisation_id = null` (central events) are visible only in central views.

### 6.3 Authorization

- `Permission` backed enum: `label()`, `description()`, `group()`, `superOnly()`. `Role` enum for the system roles `super_admin` and `organisation_admin`.
- **Super admin**: `users.is_super_admin` is the only source of truth; `User::isSuperAdmin()` reads only this column. Every super-admin rule uses it: `Gate::before`, login on any host (password, 2FA, passkeys), the impersonation matrix, the last-super-admin guard, the doctor check, the global second-factor flag. The `super_admin` role is a display badge only: protected, not assignable through `UpdateUserRoles`, and kept in sync by the `SetSuperAdmin` action (used by the users edit page, `skv:create-super-admin` and seeders), which sets the flag and attaches/detaches the role in one transaction and enforces the last-super-admin guard (counting active, non-deleted users with the flag). `permissions:sync` and doctor `--fix` repair drift.
- `permissions:sync`: upserts the catalogue, maintains the organisation admin role(s) per the S2 outcome, prunes removed permissions. Runs in setup, on deploy, and via doctor `--fix`.
- `withPermissionsTeam(?int $teamId, Closure $fn)` with `finally`; an arch test bans `setPermissionsTeamId()` elsewhere.
- **Spike S2** decides between (A) one global `organisation_admin` template role (`team_id = NULL`) assigned per team and (B) one role row per organisation (skv2 D8). Consequences:
  - `UpdateUserRoles`: under A the only accepted null-team role is `organisation_admin`, always attached with the target organisation's team id; under B every null-team role is rejected.
  - `permissions:sync`: A upserts the single template; B (re)creates and resyncs every organisation's role, and the organisation observer creates it on create.
  - Doctor: A checks the template exists with the current permission set; B checks every organisation has its role.
  - Roles index: under A the template is protected like `super_admin` (it already is as a system role).
  The M2 plan is written after S2; the outcome is recorded in `docs/decisions.md`.

### 6.4 Cross-host handoff

Super admins (and slug renames) move between hosts with a single-use signed token: `/auth/handoff/{token}` on the target host, valid 60 seconds, bound to the user and target host, consumed on use, audited. Session cookies stay host-only.

### 6.5 UI and UX

- **Layouts**: one `layouts/base` (head, `@fluxAppearance`, toasts, `@fluxScripts`, flash→`Flux::toast` bridge for `session('status')`). App and auth layouts derive from it. The setup layout (§5.3.4) and error pages do not use Vite. Unused starter layouts and components are removed; no hard-coded `class="dark"`, no `!important` hacks, one neutral palette.
- **Navigation**: one definition (route, label, icon, permission, match pattern, group, module) drives the sidebar (`flux:sidebar.*`, collapsible, groups Overzicht / Beheer / Systeem), active-state matching, the command palette (Pro), and a test that renders every item for each role × module flag.
- **User menu**: one component with language and appearance switches. Sticky impersonation banner component.
- **Branding**: `config/branding.php` (name, logo, accent) mapped to Flux accent tokens; set during setup.
- **Appearance (DEC-12)**: Flux keeps the choice only in per-origin `localStorage['flux.appearance']` (`AssetManager::fluxAppearance()`). For authenticated users `layouts/base` prints an inline script **before** `@fluxAppearance` that sets that key from `users.appearance` (or removes it for `system`), and renders `class="dark"` on `<html>` server-side when the value is `dark`, so there is no flash and the choice is the same on every subdomain. The switch binds `$flux.appearance` and saves `users.appearance` through a Livewire action; logout removes the key. Guests follow `prefers-color-scheme`. Mails stay light. Tests: the `dark` class per stored value; a browser test that the choice survives a subdomain switch.
- **Dashboard**: Organisation and "Your roles" cards for everyone (§4.10); stat cards and recent activity only with the matching permissions (activity: `activity_log.view`); onboarding checklist for super admins and organisation admins (create organisation, invite admin, enable 2FA, set branding), hidden when complete; logins-over-14-days chart with Pro.
- **Local quick login**: account switcher for the demo accounts, shown only when `app()->isLocal()`, the marker records `start_with=demo` and the demo accounts exist.
- **Settings**: profile (name, email, language, avatar), appearance, security (password, 2FA with improved recovery codes, passkeys when the module is on, active sessions).
- **System page** (`system.index`, `can:system.health`): doctor checks + cached health results.
- **Localisation**: supported locales defined once (config + `Locale` enum) and used by validation, migration default, factory, selects and switchers. Ship `lang/nl/{auth,passwords,validation,pagination}.php`, `lang/nl.json`, `lang/en.json`. `#[Title]` values translated. `label()` (and `color()` for badges) on status, role, permission and activity enums. Guests get a locale from `Accept-Language`; auth pages have a language toggle. Only `nl`/`en` vendor translations kept. A test asserts both JSON files have identical keys.
- **Error pages**: self-contained (inline CSS, no Vite, dark mode via media query), localised (user → `Accept-Language` → default), contextual actions (419 reload, 403 back / switch organisation, guests get a login link).

### 6.6 v1 extras (DEC-11)

- **Sessions**: Settings → Security lists the user's rows from `sessions` (device and browser parsed from `user_agent` by a small in-house parser, IP, last active, "this device"). "Log out other devices" requires the password: `Auth::logoutOtherDevices($password)` (rehashes the password and refreshes this device's remember cookie), then delete the user's other `sessions` rows. Remember-me logins elsewhere are cut off because `AuthenticateSession` runs on every authenticated request (§4.2). Audited. Tests: a second "remember me" client is unauthenticated on its next request; the current device stays logged in; other rows are gone.
- **Second factor required per organisation**: `organisations.require_second_factor` (default false), editable by organisation admins and super admins, audited. Satisfied by a confirmed TOTP secret, or by at least one passkey when the passkeys module is on (module off → only TOTP counts and the UI says "2FA"). Enforced on every authenticated request by `EnsureSecondFactor`, attached to the authenticated app route group (not the global `web` group). It lets a request through when: the session is an impersonation session; it is a Livewire update/upload request; or the route name matches `config('skv.second_factor.exempt_routes')` (default: `security.edit`, `password.confirm`, `password.confirm.store`, `password.confirmation`, `two-factor.*`, `passkey.*`, `passkeys.*`, `well-known.passkeys`, `logout`, `auth.handoff`, `impersonation.stop`, setup-wizard routes). Unsatisfied users are redirected to `security.edit` with an explanation. Super admins: `config('skv.second_factor.super_admins')` (env `REQUIRE_SECOND_FACTOR_SUPER_ADMINS`, default false), on every host. Tests: redirect from the dashboard; password confirmation without a loop; enabling TOTP and, separately, registering a passkey; dashboard reachable afterwards; navigating away is blocked; module-off case.
- **Audit CSV export**: streamed download honouring the current filters and tenant scope; gated by `activity_log.view`; audited.
- **Bulk invitations**: paste addresses or upload a CSV (email, optional locale) via `flux:input type="file"` + `WithFileUploads`; per-row validation; preview; result summary (sent / skipped with reason); reuses the invite action; queued mails.
- **Avatar upload**: `flux:input type="file"` + `WithFileUploads`, `accept="image/jpeg,image/png,image/webp"`, `image|max:2048`, `flux:avatar` preview. Stored on the `public` disk under a per-organisation path; resized server-side to max 512px with a square crop (`intervention/image`, GD); old file removed on replace; initials fallback everywhere avatars appear.

### 6.7 Flux Pro layer (DEC-02)

- `Skv::hasFluxPro()` = `InstalledVersions::isInstalled('livewire/flux-pro')`, cached.
- **Rule**: no Blade view outside an `@if (Skv::hasFluxPro())` branch may use a component that exists only in the `flux-pro` stubs (verified in skv2's vendor: `tabs`, `tab`, `file-upload`, `file-item`, listbox/searchable/multiple `select` variants, `date-picker`, `command`, `chart`, plus `autocomplete`, `pillbox`, `popover`, `calendar`, `editor` — final list from spike S4). A lint test greps `resources/views` for `<flux:` names missing from `vendor/livewire/flux/stubs` and fails unless they sit inside a Pro branch.
- **Core features — free implementation (required), Pro variant (optional)**:

| Feature | Free | Pro |
|---|---|---|
| Role assignment (user edit, invite, bulk invite) | `flux:checkbox.group` | `flux:select variant="listbox" multiple` |
| Active / archived views | `flux:radio.group variant="segmented"` bound to `#[Url] $view` | `flux:tabs` |
| Avatar and CSV upload | `flux:input type="file"` | `flux:file-upload` / `flux:file-item` with preview |
| Audit date range | two date inputs | `flux:date-picker` range |
| Navigation search | — | ⌘K `flux:command` palette |
| Dashboard trend | stat cards only | `flux:chart` logins over 14 days |

  Livewire properties are identical in both variants (e.g. `array $roles`).
- **Composer**: the kit's committed `composer.json` and `composer.lock` never reference `livewire/flux-pro` or `composer.fluxui.dev`, so every install path works without credentials; a test fails if either file contains `flux-pro`. `php artisan skv:flux-pro` (for generated apps) adds the repository and requires the package using the user's global Composer credentials (`composer config --global http-basic.composer.fluxui.dev <email> <key>`, documented in the README).
- **CI**: Pro is enabled per job after `composer install` (`composer config http-basic…` from `FLUX_USERNAME` / `FLUX_LICENSE_KEY` + `skv:flux-pro --no-interaction`) and never committed. The step is skipped when the secrets are absent (fork PRs); no job is skipped.

### 6.8 Optional modules (DEC-08)

- **Flags**: `config('skv.modules.passkeys|backups|impersonation')`, read from `MODULE_PASSKEYS`, `MODULE_BACKUPS`, `MODULE_IMPERSONATION` (default true). `backups` is always false when `DB_CONNECTION=sqlite`. Setup writes the `.env` keys (never literal config values). Re-enabling = change the env key and run `skv:doctor --fix`. Migrations always run regardless of flags.
- **Impersonation off**: start route and `DELETE /impersonation` not registered; users-index action and banner hidden; `users.impersonate` stays in the catalogue (stable sync) but is hidden in the role editor; `Gate::define('impersonate')` returns false.
- **Passkeys off**: passkey routes and `.well-known/passkey-endpoints` not registered; login button and Settings → Security passkeys section hidden; passkey rate limiter and origin listener not registered; second-factor rule accepts only TOTP; HTTPS no longer forced.
- **Backups off**: `backup:*` not scheduled; the last-backup health check and the `pg_dump` doctor check report `skipped` (never a 503).
- **Demo data** is not a runtime flag (see quick login, §6.5).
- **Tests**: navigation and module feature tests run as a dataset over the flag (on → works; off → 404 and hidden). The `sqlite-free` CI job sets `MODULE_PASSKEYS=false` and `MODULE_IMPERSONATION=false`, so the all-off path runs in CI.

## 7. Quality pipeline

### 7.1 Static analysis and refactoring
- **Larastan** level 8, no baseline. Paths: `app`, `bootstrap/app.php`, `config`, `database`, `routes`, `tests`, `resources/views` (PHP only; `excludePaths: resources/views/*.blade.php`). Livewire MFC files are a bare `new class extends Component {…}` expression, and `$this->view()` is injected only at compile time, so: (1) phpstan.neon has exactly one documented, path-scoped `ignoreErrors` entry (`identifier: expr.resultUnused`, `path: resources/views/*`); no inline or blanket ignores; (2) kit components never call `$this->view()` — they pass data via `with(): array` or `#[Computed]` and omit `render()`; a test in `composer check` fails on `$this->view(` under `resources/views`.
- **Rector**: `withComposerBased(laravel: true)`, PHP 8.4 sets, prepared sets (dead code, code quality, type declarations); same paths and Blade exclusion via `withSkip`.
- **Pint**: per DEC-06.

### 7.2 Tests (Pest 5)
- Tenancy testing API: `onTenant($org)`, `onAdminHost()`, `asSuperAdmin()`, `asOrgAdmin($org)` set host and root URL so tests call `get(route(...))` directly.
- Permissions seeded once per process; `--parallel`.
- Arch tests: `php`, `security`, `laravel` presets (with justified `->ignoring()`), plus kit rules — tenant models use the trait and are cascaded; no permission literals; no `env()` outside `config/`; `setPermissionsTeamId` only in the helper; `Tenant::bypass()` only in allowed namespaces; actions don't depend on Livewire; no `ilike` or other driver-specific SQL in `app/` and `resources/views/` (DEC-03).
- **Name-leak test**: no app-identity value may contain `skv` or another hard-coded site name — defaults for `APP_NAME`, `APP_URL`, `DB_DATABASE`, the test DB name, `MAIL_FROM_ADDRESS`, seeded/demo emails, `tenancy.apex_domain`. Scans `config/`, `.env.example`, `phpunit.xml`, `database/seeders/`, `tests/`; allow-list: the `skv:` command namespace, `config/skv.php` and `config('skv.…')` keys, the `Skv` facade, the `skv-*` storage files, `.ai/guidelines/skv3.md`, `frankcornet/skv3` in `composer.json`.
- Datasets: impersonation matrix, route × host × role matrix, setup steps, permission catalogue, module flags.
- Security regression tests for every finding in Appendix A, written failing first.
- Phase-1 tests: after each of `laravel new --using` with `--database=sqlite`, without `--database`, `composer create-project` and `git clone` + `composer setup`, `.env` exists, `APP_KEY` is set and `GET /welcome-setup` (with token) returns 200 on SQLite; the wizard renders without `public/build`.
- Wizard tests: no token / wrong token / forwarded header → 404; completion deletes the token; QUEUE=database with no worker still completes; a `long()` step reaches a terminal state through polling; changing `APP_NAME` causes no 419; switching to PostgreSQL completes without a 500 or 419 (and the SQLite variant).
- Browser tests: login, invitation acceptance, impersonation, password reset, setup wizard (both DB answers), appearance across subdomains.
- `tests/Fixtures/e2e-answers.json` covers every `--answers` key; a test asserts the schema.

### 7.3 Schema dumps
The kit commits no `database/schema/pgsql-schema.*`: fresh installs, the wizard (php-fpm without Herd's Postgres binaries on PATH) and CI run plain migrations; no setup path depends on `psql`/`pg_restore`/`pg_dump`. Optionally `database/schema/sqlite-schema.sql` is committed for the in-memory test connection (loaded via PDO), with a CI check that fails when it is stale.

### 7.4 Scripts and hooks
- **Composer scripts**: `setup` (§5.3.3), `dev` (Vite, queue, Pail, `schedule:work`; no `serve` under Herd), `fix` (rector → pint), `check` (pint --test, rector --dry-run, phpstan, the `$this->view(` check, pest --parallel excluding browser), `test:browser` (checks Playwright first and prints the fix), `doctor`.
- **Git hooks**: `.githooks/pre-commit` (< 10 s: `pint --dirty`, phpstan on changed files); full suite in CI.

The e2e job runs without Flux credentials in its default variant, proving the credential-free path.
