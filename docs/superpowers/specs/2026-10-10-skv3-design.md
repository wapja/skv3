# skv3 — Design Spec

- **Date:** 2026-10-10 (rev. 2, after multi-lens review)
- **Status:** Accepted for v1 (M8a); amended in place by the build decisions DEC-25…DEC-36 in `docs/decisions.md`
- **Predecessor:** `~/Herd/skv2` (spec `docs/superpowers/specs/2026-07-19-skv2-spec.md`, decisions D1–D34 in its README)
- **Package:** `frankcornet/skv3` (`"type": "project"`, MIT, public GitHub + Packagist)

## 1. Goal

skv3 is an opinionated, multi-tenant Laravel starter kit. It keeps **all** functionality of skv2 and is more modern, more user-friendly and much easier to set up. The headline experience:

> Herd → *New site* → *Custom Starter Kit* `frankcornet/skv3` → *Open site* → a browser setup wizard (at most 5 questions, pre-filled) → a working, seeded app. Under 5 minutes, no file edits, no terminal needed on the default answers.

The same setup is available as `php artisan skv:install` for terminal users, CI and AI agents.

### 1.1 Non-goals (v1)

- Multi-database tenancy, per-organisation custom domains, Postgres row-level security.
- Path-based tenant identification (the resolver sits behind an interface so it can be added later).
- Billing (Cashier/Spark/Paddle), Filament, a Laravel MCP app server, an in-app `/docs` route.
- Switching to stancl/tenancy or spatie/laravel-multitenancy.
- Languages beyond `nl` and `en` (the language list is config-driven).
- Telescope (replaced by Debugbar + Pail + Herd Dumps/Log Viewer).
- Membership of more than one organisation per user.
- Self-service account deletion (skv2 D33 carried over).

## 4. Feature inventory (parity checklist)

Every item must exist in skv3 and be covered by at least one test. "→" marks a change from skv2.

Traceability (M8a, CD-17): every bullet starts with a frozen id `§4.x.n`. Ids are never renumbered: a new bullet takes the next free number of its subsection, and the id of a removed bullet is never reused. Each test file starts with a `covers` docblock line that cites the bullet ids it tests (a plain `§4.x` names the subsection and cites none of its bullets). `php scripts/traceability.php` lists the bullets no test cites and the cited ids §4 does not have, and exits 1 when there are any; `tests/Feature/Tooling/TraceabilityTest.php` runs it.

### 4.0 App defaults
- §4.0.1 `AppServiceProvider::configureDefaults()`: `Date::use(CarbonImmutable::class)`; `DB::prohibitDestructiveCommands(app()->isProduction())`; strong `Password::defaults()` in every environment except `local` and `testing` (DEC-34 (10), amended in M7c: staging and other environments get the production rule); `Model::shouldBeStrict(! app()->isProduction())` (enabled by the end of M2 at the latest, with scoped exceptions per §13).
- §4.0.2 Tests: `now()` is `CarbonImmutable`; `migrate:fresh` / `db:wipe` refused in production.

### 4.1 Multi-tenancy
- §4.1.1 Single database; organisation resolved from the subdomain: `{slug}.{apex}` = tenant host, `{apex}` and `admin.{apex}` = central hosts.
- §4.1.2 → Env: `TENANCY_APEX_DOMAIN` (default: `APP_URL` host), `TENANCY_ADMIN_SUBDOMAIN` (default `admin`).
- §4.1.3 Resolver binds the current organisation, sets the Spatie team id, clears state on central hosts. Unknown or soft-deleted slugs → friendly tenant 404 with a link to the apex.
- §4.1.4 Global organisation scope + `BelongsToOrganisation` trait (auto-fill `organisation_id`, `organisation()` relation).
- §4.1.5 Unscoped auth user provider for sessions, password broker, 2FA and passkey lookups.
- §4.1.6 Membership middleware: logs out inactive users / users on the wrong host. → With a flash message explaining why; impersonation ends cleanly (with `impersonation.stop` logged) instead of logging the impersonator out.
- §4.1.7 Tenant URL helper with `APP_URL`'s scheme **and port**, never the request's (§6.2, DEC-34).
- §4.1.8 Config: apex domain, admin subdomain, tenant models list (soft-delete cascade), reserved slugs.
- §4.1.9 Soft-deleting an organisation soft-deletes its tenant models with the same timestamp; restore restores only those rows; force delete does not cascade (purge is explicit, §4.3).
- §4.1.10 Host-only session cookies (`SESSION_DOMAIN=null`) → per-subdomain sessions.
- §4.1.11 Tenant name in the brand on tenant hosts.

### 4.2 Authentication (Fortify)
- §4.2.1 Login scoped per host: an active user that belongs to the current host; super admins log in on any host. 2FA and passkey login use the same rule.
- §4.2.2 Registration and email verification disabled; invite-only.
- §4.2.3 Password reset. → The reset URL points at the user's own host (`ResetPassword::createUrlUsing` + `tenant_url()`); neutral status message whether or not the address exists; `password.email` throttled; tests run on tenant hosts.
- §4.2.4 TOTP 2FA: enable/confirm/disable with QR + setup key, password confirmation, recovery codes (show/hide/regenerate). → Copy, download, confirm-before-regenerate.
- §4.2.5 Passkeys (module, §6.8): register/list/delete, login from the login page, `.well-known/passkey-endpoints`. → The RP id is **always the apex** (`passkeys.relying_party_id`, override `PASSKEYS_RELYING_PARTY_ID`), a valid registrable suffix for the apex, `admin.{apex}` and every `{slug}.{apex}`. It never changes per request, so one passkey works on every host the user may log in on and survives a slug rename. Only `passkeys.allowed_origins` changes per request: set to the current request's host with `APP_URL`'s scheme and port (`Hosts::origin()`, DEC-34) on `TenantResolved` / central resolution, reset on `TenantForgotten`. These are the `passkeys.*` keys the package reads at request time — not `fortify.passkeys.*` (skv2's no-op). Login is authorised by `Passkeys::authorizeLoginUsing()` with the host rule above; passkey users load through `UnscopedPasskey::user()`, a relation that reads users without the tenant scope and includes deleted users so the host rule can refuse them, instead of `Passkeys::useUserModel()` with a second user model (DEC-27 (4); skv2 returned null → 500 for super admins).
- §4.2.6 Password confirmation flow.
- §4.2.7 Rate limiters for login (email+IP, IP), two-factor, passkeys. → Count only failed attempts.
- §4.2.8 Lower-cased emails.
- §4.2.9 → Changing the email address requires confirmation via a signed link to the new address and a notice to the old address (M3, DEC-25).
- §4.2.10 `Illuminate\Session\Middleware\AuthenticateSession` on every authenticated route (needed for §6.6 sessions). → It runs in the `web` group, so on every authenticated route (DEC-35 (11)).

### 4.3 Organisations
- §4.3.1 Model: name (unique), slug (unique), description, soft deletes. → `require_second_factor` (bool, default false, §6.6). → The second-factor rule is edited on `organisations.edit` (§6.6).
- §4.3.2 Index (tenant host shows only its own), create, edit, soft delete.
- §4.3.3 → Archived view with restore and purge. `restore` = `organisations.delete`. **Purge** (force delete) is only available for archived organisations, gated by a `forceDelete` policy ability mapped to `organisations.delete`, requires typing the slug, and runs a `PurgeOrganisation` action in one transaction, deleting in order: invitations, users including trashed ones (passkeys and handoff tokens cascade by foreign key; `sessions` rows and the users' `password_reset_tokens` have no foreign key and are deleted explicitly; promoted super admins are detached, not deleted; the deleted users' avatar files are deleted after commit, built in M7d, and a detached super admin keeps theirs) (DEC-28), team roles and the `model_has_roles` / `model_has_permissions` rows for its team id, then the organisation. Activity rows are kept (`activity_log.organisation_id` has no FK). Logs `organisation.purged`. `users.organisation_id` keeps `restrictOnDelete` as a safety net.
- §4.3.4 Policy: view/update = permission + ownership; create/delete/restore/forceDelete = super admin.
- §4.3.5 Slug rename redirects to the new subdomain (via the handoff token, §6.4). → Only super admins change the slug; organisation admins see it read-only. The old slug is free at once; old slugs are not reserved or redirected in v1 (DEC-28).
- §4.3.6 `organisation_admin` role available for every organisation (mechanism per spike S2, §6.3).
- §4.3.7 Super-admin tenant picker. → Merged into the organisations index ("Open" action using the handoff token).
- §4.3.8 → Slug rule: `[a-z0-9-]`, 3–63 chars, no leading/trailing hyphen, not in `config('tenancy.reserved_slugs')` (default: `admin`, `www`, `api`, `app`, `mail`, `smtp`, `ftp`, `static`, `assets`, `cdn`, `docs`, `help`, `status`, `support`, `dashboard`, `login`, `test`).
- §4.3.9 → Organisation wizard: name, slug (auto, live availability, `slug.apex` preview), first admin's email → creates the organisation and sends the invitation.

### 4.4 Users
- §4.4.1 Soft deletes, status enum (`pending_activation`, `active`, `disabled`), per-user locale, audit logging of fillable fields except password.
- §4.4.2 Super admin. → Explicit `is_super_admin` boolean, the only source of truth (§6.3).
- §4.4.3 Index: search, status filter, role filter, 25 per page, organisation column and roles on the admin host, delete modal, impersonate action (tenant host, module on). → Search is case-insensitive on both drivers via `whereLike(..., caseSensitive: false)`; no raw `ilike`/`like`. → Archived view with restore: `restore` = `users.delete` + same organisation; refused while the organisation is archived or when the email is now taken by a non-deleted user.
- §4.4.4 Edit page doubles as show page: name, email, status, roles (`roles.assign`). → `pending_activation` cannot be set by hand; email uniqueness uses `withoutTrashed()` everywhere.
- §4.4.5 Policy: view, update, delete (not yourself), impersonation matrix.
- §4.4.6 Factory states: pending, disabled, superAdmin, withTwoFactor (`unverified` was removed with `email_verified_at`, DEC-27 (7)).
- §4.4.7 Email unique among non-deleted users: the users migration creates `email` without a unique constraint, then one `CREATE UNIQUE INDEX users_email_unique ON users (email) WHERE deleted_at IS NULL` (valid on Postgres and SQLite). No `ALTER TABLE … DROP CONSTRAINT`.
- §4.4.8 → Avatar upload (§6.6): `users.avatar_path`, nullable. → `users.appearance` (DEC-12).

### 4.5 Invitations
- §4.5.1 Invite by email with locale and roles; user created as pending. → At least one role required.
- §4.5.2 Invitation: token, `expires_at` (configurable, default 7 days), `reminder_sent_at`, `accepted_at`, inviter.
- §4.5.3 → Accept URL built in one place: `Invitation::acceptUrl()` = `tenant_url($org, URL::temporarySignedRoute('invitations.accept', $expires_at->addDays(config('skv.invitations.signature_grace_days', 30)), ['token' => $token], absolute: false))`; the route uses `signed:relative` so it survives http↔https and host rewrites between queueing and clicking. **Two-layer expiry:** `expires_at` (domain expiry) is checked in the accept component and renders the "expired" page with the resend button; the signature lives longer so only links older than the grace period get a 403. Never sign with `expires_at` itself.
- §4.5.4 Actions: invite, accept, remind, cancel (cancel hard-deletes the invitation and soft-deletes the pending user). → Team-id switching via `withPermissionsTeam()` (`finally`).
- §4.5.5 Markdown mails: invitation, reminder. → Queued (`ShouldQueue`), `afterCommit`.
- §4.5.6 Pending list: inviter, relative expiry, remind (`users.invite.resend`), cancel (`users.delete`). → Crash-proof with a deleted inviter (`withTrashed`, null-safe). → Remind refused for accepted invitations.
- §4.5.7 Accept page: set password; expired state; resend button for authorised users. → Invitee chooses their own name; logged in after accepting; separate "already accepted — please log in" state.
- §4.5.8 Audit events: sent, reminder sent, accepted, cancelled.
- §4.5.9 Re-inviting an address after cancel works.
- §4.5.10 → The `invitations` table is the single source of truth (no `users.activation_*` columns).
- §4.5.11 → "Copy invite link" button. → Super admins can invite from the admin host by picking an organisation.
- §4.5.12 → Bulk invite built (§6.6, M7d). → Generic "this address can't be invited" message (no cross-organisation enumeration). → Every check of a typed address (the profile's email change, `users.edit`, `users.invite` and each row of the bulk page's *Check*) counts under `UserActionLimit::addressLookup()`, 500 a day per user, refused ones too, so an account cannot list which addresses have one; during an impersonation the impersonator pays, and the profile refuses a new address before any lookup (FM-18, DEC-36 (2)).

### 4.6 Roles and permissions (spatie/laravel-permission, teams mode)
- §4.6.1 15 permissions: `users.view/create/update/delete/invite.resend/impersonate`, `roles.view/assign/manage`, `organisations.view/create/update/delete`, `activity_log.view`, `system.health`.
- §4.6.2 Super-only: `roles.manage`, `organisations.create`, `organisations.delete`, `system.health`.
- §4.6.3 Global `super_admin` role (display badge only, §6.3); `organisation_admin` = catalogue minus super-only.
- §4.6.4 `Gate::before` grants super admins everything except `impersonate` and the self-destructive abilities, which return `null` so policies and guards always run.
- §4.6.5 Roles index with a "System roles" group carrying a "Protected" badge (DEC-29, FU4-5), permission badges, CRUD under `roles.manage`. → **System roles** (`Role` enum: `super_admin`, `organisation_admin`) cannot be renamed, deleted or used as a new role's name; their permissions are read-only in the UI and owned by `permissions:sync`. Custom roles are always team-scoped: created on a tenant host, or on the admin host only after an organisation is explicitly picked; a null-team custom role is never created; custom roles never receive super-only permissions. Role lookups by id are scoped to the current team (fixes W1's cross-team edit).
- §4.6.6 Pivot primary keys exclude `team_id` (null team allowed, skv2 D28).
- §4.6.7 Route-level `can:` middleware and permission-gated navigation.
- §4.6.8 → `Permission` and `Role` backed enums; no permission string literals in app code.
- §4.6.9 → Idempotent `permissions:sync` command.
- §4.6.10 → Role assignment only via an `UpdateUserRoles` action with full authorisation; roles validated against the target organisation's team; null-team roles rejected except as allowed by the S2 outcome (§6.3) (fixes W1).
- §4.6.11 → Guards: last super admin, last organisation admin, removing your own admin role, disabling yourself (fixes W2, W12).

### 4.7 Impersonation (module, §6.8)
- §4.7.1 Reason required (non-blank, ≤ 500 chars), `Gate::authorize('impersonate')`, depth 1.
- §4.7.2 Matrix: target never a super admin; super admin may impersonate anyone; others only same-organisation non-admins; tenant host only. → Target must be active (fixes W3).
- §4.7.3 Audit `impersonation.start` (with reason) / `impersonation.stop`; causer rewritten to the real user, `impersonated_as` recorded.
- §4.7.4 Sticky banner with stop button; `DELETE /impersonation`. → "Stopped" toast is shown.

### 4.8 Audit log (spatie/laravel-activitylog v5)
- §4.8.1 Custom Activity model: causer rewrite during impersonation; organisation tagging; diffs in `attribute_changes`.
- §4.8.2 Authentication subscriber: login, login failed (with email), logout, password reset requested/completed, 2FA enabled/disabled. → Also failed 2FA codes and used recovery codes; a failed login keeps the typed value only when it is a valid email address, never the password (DEC-28).
- §4.8.3 Viewer: date range, action, subject type, causer filters; 50 per page; diff and reason columns; tenant-scoped; cross-scope causer names.
- §4.8.4 Dashboard widget: last 10 entries. → Gated by `activity_log.view`; causers resolved without the tenant scope.
- §4.8.5 → Real indexed `organisation_id` column (no FK), `created_at` index, IP + user agent captured.
- §4.8.6 → `ActivityEvent` enum with translated labels.
- §4.8.7 → Also logged: organisation CRUD/purge, role/permission changes, role assignments, security settings (password, passkeys, recovery codes, sessions, second-factor setting). → M7d adds `security.other_sessions_ended` (with `properties.count`) and `audit.exported` (a new group `audit`, which tags by host); the second-factor setting rides on `organisation.updated`, and an avatar change on `user.updated` (`attributes.avatar` = `set` or `removed`, never the path) (DEC-35 (9)).
- §4.8.8 → Filters in the URL (`#[Url]`), `resetPage()` on filter change, detail flyout, CSV export (§6.6). → The CSV export is built (M7d).
- §4.8.9 → Retention: published `config/activitylog.php` sets `clean_after_days => (int) env('ACTIVITYLOG_RETENTION_DAYS', 365)`; `actions.clean_log` points to `App\Actions\Audit\CleanActivityLog`, which runs the delete inside `Tenant::bypass()`.

### 4.9 Ops
- §4.9.1 `/up`: framework liveness route (no auth; 200, or 500 on failure). Documented as liveness only.
- §4.9.2 `/health-check`: registered outside the web group (`withRouting(then:)`), `throttle` only — no session, cookies, tenant or locale middleware. Authorised only by header `X-Health-Check-Key`, `hash_equals` against `HEALTH_CHECK_KEY`; a blank or missing configured key always → 403. Checks: database, queue (failed jobs; not ok when the table is missing), mail (SMTP probe only when `MAIL_MAILER=smtp`; any other mailer passes with a message that names it and opens no socket, DEC-36 (24) (d)), last backup (skipped when the backups module is off). JSON; 200 when all pass, 503 when any fails; results cached briefly. → skv2's `system.health` permission path (D10) moves to the System page (§6.5), which shows the same cached results.
- §4.9.3 Backups (module, §6.8): database only, encrypted, monitored. → Off on SQLite; last-backup time read via the backup destination API; `BACKUP_ARCHIVE_PASSWORD`, `BACKUP_NOTIFY_EMAIL` in `.env.example`; failure-only notifications; `pg_dump` auto-detected (`PG_DUMP_BINARY_PATH`).
- §4.9.4 Scheduler (with `onOneServer()` + `withoutOverlapping()`): `backup:clean` 01:30 and `backup:run --only-db` 02:00 (module on), `backup:monitor`, `queue:prune-failed`, `auth:clear-resets`, `activitylog:clean --force` (the command uses `ConfirmableTrait` and cancels itself in production without `--force`). `model:prune` only once a model is prunable. → Built (M7a–M8a): `model:prune` removes the expired handoff tokens; `backup-temp-cleanup` (hourly at :15) and `livewire-tmp-cleanup` (hourly at :45: Livewire's temporary uploads older than 24 hours, nothing on an S3 temporary disk or while `livewire.temporary_file_upload.cleanup` is false; DEC-36 (4)) run on every server without an overlap lock; the `scheduler-heartbeat` runs every minute.
- §4.9.5 Custom error pages 403/404/419/429/500/503. → Self-contained (§6.5).

### 4.10 UI shell and settings
- §4.10.1 Sidebar layout with permission-gated navigation, mobile header, user menu, toasts.
- §4.10.2 Settings: profile (name, email, language), appearance (light/dark/system), security (password, 2FA, passkeys).
- §4.10.3 → No self-service account deletion (D33): M1 removes the starter kit's delete-user form, component, view and include. Test: the profile page renders no delete-account control and no route or action deletes `auth()->user()` outside the admin users flow.
- §4.10.4 Dashboard: for every signed-in user, an Organisation card (current organisation; "Platform" on central hosts) and a "Your roles" card with translated role badges ("No roles assigned" when empty).
- §4.10.5 → Everything else in §6.5.

### 4.11 Localisation
- §4.11.1 `nl` default, `en` fallback; per-user locale middleware.
- §4.11.2 → Guests get a locale from `Accept-Language` (changes skv2 D17); see §6.5.

### 4.12 Seeding
- §4.12.1 Permission catalogue + `super_admin` always seeded (essentials seeder, idempotent).
- §4.12.2 Demo data: super admin, organisations `demo1` and `demo2`, each with an admin and a user. → Split into an essentials seeder (always) and a demo seeder (optional, refuses to run in production); emails derived from the apex; demo users share the password `password`, printed in the setup summary. → `skv:create-super-admin` and `skv:create-organisation` commands.

## 5. Setup and distribution

### 5.1 Entry points

1. **Herd wizard**: *New site* → *Custom Starter Kit* → `frankcornet/skv3`, or the deep link `https://herd.laravel.com/new/frankcornet/skv3`.
2. **Terminal**: `laravel new myapp --using=frankcornet/skv3` (with or without `--database`).
3. **Composer**: `composer create-project frankcornet/skv3 myapp`.
4. **Clone/template**: `git clone https://github.com/frankcornet/skv3.git` → `composer setup`.

All four end in the same phase 2 (§5.3).

### 5.2 Phase 1 — create (non-interactive)

Installer facts this design relies on (installer 5.31.1 and 5.32.0, Herd 1.30.2):
- Herd's GUI runs `laravel new <name> --no-interaction --no-ansi --database=sqlite --npm …` plus its checkbox flags (testing framework, git, Boost). There is no TTY; prompts take their defaults.
- The installer runs `composer create-project <kit> <dir> --stability=dev` (no version) with `LARAVEL_INSTALLER_DEFER_HOOKS=1`. With `--stability=dev`, Composer installs the **default branch** (`dev-main`), not the latest tag (DEC-18).
- Then: `post-root-package-install` again, `key:generate`, the kit's `extra.laravel.installer.post-create-project` commands, a rewrite of every literal `php-version: 'x.y'` in `.github/workflows/tests.yml`, the `APP_URL` rewrite (`http://<name>.test` when parked and resolvable, else `http://localhost[:8000]`), and the `DB_*` rewrite + `migrate` **only when `--database` is passed** (otherwise the kit is expected to migrate itself).
- Herd Pro mail rewrite (`MAIL_MAILER=smtp`, Herd's SMTP port, `MAIL_USERNAME`), optional `git init` + commit (after the kit hooks), optional Pest (`composer remove phpunit` → `composer require pest…` → full `composer update` → `pest --init` → drift round trip → edits `tests.yml` and `tests/Pest.php`), npm install + build (failure ignored), optional Boost (`composer require "laravel/boost:^2.2" -W`, `boost:install`, appends `boost:update` to `post-update-cmd` without a duplicate check).
- The kit's hooks run **before** the DB rewrite, migrate and `git init`.

Kit rules that follow:
- **Composer hooks:**
  - `post-root-package-install`: `@php -r "file_exists('.env') || (copy('.env.example', '.env') && chmod('.env', 0600));"`
  - `post-create-project-cmd`: `@php artisan skv:bootstrap --no-interaction --ansi`
  - `extra.laravel.installer.post-create-project`: `@php artisan skv:bootstrap --no-interaction`
- **`skv:bootstrap`** returns early when `LARAVEL_INSTALLER_DEFER_HOOKS` is set. Otherwise it is idempotent and does exactly: (1) copy `.env.example` → `.env` if missing; (2) generate `APP_KEY` if empty; (3) if `APP_URL` is `http://localhost[:8000]` and Herd is present, rewrite it to `http://<folder>.<herd tld>` (mirrors the installer's `generateAppUrl`); (4) if `DB_CONNECTION=sqlite`, touch `database/database.sqlite` and run `migrate --graceful --force`; (5) create the one-time setup token (§5.3.4); (6) print "Open <APP_URL>/welcome-setup". It never chooses a database, never prompts, never caches config/routes, and respects `LARAVEL_INSTALLER_NO_NODE`. In the Herd route the installer's later `migrate` is a no-op. → In production (an `APP_ENV` outside `local`, `testing` and `staging` in `.env` or the process environment, or none in any source, which Laravel treats as `production`; DEC-33, DEC-36 (12)) it only prepares `.env`, `APP_KEY` and the generated secrets.
- **`.env.example`** keeps Laravel's default lines so the installer's replacements match: `APP_URL=http://localhost`, `DB_CONNECTION=sqlite`, commented `# DB_HOST=127.0.0.1` … `# DB_PASSWORD=`, `MAIL_MAILER=log`, `MAIL_PORT=2525`, `MAIL_USERNAME=null`. It also ships `SESSION_DRIVER=database`, `SESSION_COOKIE=app_session` (fixed and neutral, §5.3.3), `HEALTH_CHECK_KEY=`, `TENANCY_APEX_DOMAIN=`, `MODULE_PASSKEYS=true`, `MODULE_BACKUPS=true`, `MODULE_IMPERSONATION=true`, `ACTIVITYLOG_RETENTION_DAYS=365`, `BACKUP_ARCHIVE_PASSWORD=`, `BACKUP_NOTIFY_EMAIL=`.
- **Workflows:** the kit's single CI workflow is `.github/workflows/tests.yml` (DEC-22, DEC-25). It sets PHP via `matrix.php`, never as a quoted literal, and never contains `./vendor/bin/phpunit`, so every installer edit to it is a no-op (without the file, the `--pest` step would commit an empty, invalid `tests.yml`). The kit ships no `ci.yml`.
- **`pest --init`:** the installer's Pest step recreates `tests/Feature/ExampleTest.php` and `tests/Unit/ExampleTest.php` when they are missing (the feature stub asserts `GET /` → 200, which is wrong for this kit). The kit therefore ships real tests at exactly these two paths; existing files are left alone.
- **Pest:** the kit already uses Pest; the installer's Pest step may re-resolve dependencies (`composer update`), so the kit's constraints are the real tested minimums. Spike S3 records the full diff the installer produces and the kit adjusts shipped files so the edits are no-ops.
- **Boost:** the kit's `composer.json` does not list `boost:update` in `post-update-cmd`; `skv:install` adds it once, and restores the `laravel/boost` constraint to `^2.10` if the installer lowered it.
- **Flux Pro:** never shipped and never referenced in the kit's `composer.json`/`composer.lock` (§6.7).

### 5.3 Phase 2 — set up (browser wizard or CLI)

#### 5.3.1 Setup steps

Steps live in `app/Setup/Steps/*`:

```php
interface SetupStep
{
    public function key(): string;            // stable id: progress tracking, state file, marker, UI
    public function label(): string;          // translated, user-facing
    public function isComplete(SetupContext $context): bool; // idempotency check
    public function isLong(): bool;           // runs detached in the browser (§5.3.3)
    public function run(SetupContext $context): StepResult;  // done | skipped | manual(command, reason)
}
```

A step that cannot run from the current context returns `StepResult::manual($command, $reason)`: the browser shows the command with a copy button and a "Re-check" button; the CLI prints it.

#### 5.3.2 Detection, questions and the `--answers` schema

**Detection** runs before questions are shown or `--answers` is validated: Herd present; Herd Pro and its mail service (`~/Library/Application Support/Herd/config/herd.json`: `mails`, `smtpPort`; services via `herd services:list --json`, never trusting exit codes); a reachable Postgres (try Herd's known credentials); Flux Pro installed; `claude` on PATH; current host and scheme (browser) or folder + `herd tld` (CLI).

**Questions** — this table is also the `--answers` JSON schema (`tests/Fixtures/e2e-answers.json` exercises it). The browser shows the defaults pre-filled; `skv:install --no-interaction` uses them as-is.

| Key | Type | Default |
|---|---|---|
| `app_name` | string | `Str::headline(basename(base_path()))` |
| `database` | `pgsql` \| `sqlite` | `pgsql` if a reachable Postgres was detected, else `sqlite` |
| `start_with` | `demo` \| `super_admin` | `demo`. With `super_admin`, `super_admin_email` + `super_admin_password` are required; with `--no-interaction` and either missing, the command fails before any step runs |
| `modules` | subset of `passkeys`, `backups`, `impersonation` | all three; `backups` removed on sqlite |
| `https` | bool | true; forced true while `passkeys` is on |
| `playwright` | bool | false |
| `claude` | bool | true if `claude` is on PATH, else false |

#### 5.3.3 Steps (in order)

1. **Environment file**: write `.env` atomically (temp file + rename): `APP_NAME`; `APP_URL` and `TENANCY_APEX_DOMAIN` from the browser request host (or folder + Herd TLD in the CLI); a random 40-char `HEALTH_CHECK_KEY` if empty; `APP_FAKER_LOCALE=nl_NL`; module flags `MODULE_*`; mail: when Herd Pro mail is active, `MAIL_MAILER=smtp`, `MAIL_HOST=127.0.0.1`, `MAIL_PORT=<smtpPort>`, `MAIL_USERNAME="${APP_NAME}"` unless the installer already set non-default values — otherwise keep `MAIL_MAILER=log` and say so in the summary. Existing `APP_KEY` preserved. It also creates `public/storage` with `php artisan storage:link` (a child process in the project) while it is missing, because the frontend step is skipped when a build exists (CD-12); the link left to make is `manual('php artisan storage:link')`. → Only a `public/storage` that resolves to `storage/app/public` counts (M8a, D63): a wrong or dangling link is replaced with `storage:link --force`, and a directory or a file in its place is never removed (the manual result asks to move it aside). `DB_*` is **not** written here. `APP_URL` stays http until the HTTPS step.
2. **Database (atomic switch)**: for `pgsql`, create the app database and `<db>_test` over PDO, configure the connection at runtime (`config([...])` + `DB::purge()`), migrate, `permissions:sync`, run the essentials seeder, then the demo seeder or `SetSuperAdmin` for the real super admin — and only after all of that succeeds, write `DB_*` to `.env`. For `sqlite`, migrate (if needed), sync and seed on the existing file. Writes `.env.testing` (`<db>_test`, or in-memory SQLite) with mode 0600, like the `.env` that `skv:bootstrap` creates (CD-8). Verifies that no `database/schema/pgsql-schema.*` dump is present (§7.3).
3. **`herd.yml`**: name, `php: 8.4`, `secured: <https answer>`, PostgreSQL 18 service when `pgsql`.
4. **Branding**: `APP_NAME` and accent into `.env`-backed `config/branding.php` values.
5. **Frontend** (long): if Node satisfies `^20.19 || >=22.12` and the manifest is missing or stale, `npm ci && npm run build`; optional `npx playwright install chromium`. On failure: `manual('npm ci && npm run build', reason)`.
6. **Git**: `git init` if there is no repository; `git config core.hooksPath .githooks`.
7. **Claude** (when chosen; long): `boost:install --no-interaction` (needs a `.test` `APP_URL`); generate `.mcp.json` with Boost + Herd MCP, registering the Herd MCP server as `herd` in `.mcp.json` (so the `mcp__herd__get_all_sites` deny applies, DEC-25); `claude plugin install superpowers --scope project` if `claude` is on PATH; add `boost:update` to `post-update-cmd` once.
8. **Doctor**: run `skv:doctor` (§5.4).
9. **Marker**: write `storage/app/skv-installed` (JSON: kit version, answers without secrets, `start_with`, timestamp, summary). Delete `storage/app/private/skv-setup-token` and `storage/app/private/skv-setup.json`.
10. **Herd site** (last): (a) parked = the parent of `base_path()` is in `herd paths` (JSON); if not parked and not in `herd links`, `herd link <name>` (no `--update-env`/`--secure`/`--isolate`; `link` also runs `boost:update` when Boost exists, which is acceptable at this point); (b) when HTTPS is on: `herd secure <name>`, then rewrite `APP_URL`/apex to https in `.env` in-process (`herd secure` has no `--update-env`); (c) `herd isolate 8.4 --site=<name>` only when the site would be served by PHP < 8.4 and is not isolated — in the browser this is always `manual(...)` because isolate restarts php-fpm. → The step is complete only while Herd serves the site with PHP 8.4 or newer, so a re-run on a site served with an older PHP reaches the isolate (K9, DEC-36 (23)).
11. **Summary**: clickable URLs (apex, admin host, demo tenants), logins (demo: emails + `password`) or "log in as <email>", next steps, any `manual()` commands left.

`composer setup` = `["Composer\\Config::disableProcessTimeout", "composer install", "@php -r \"file_exists('.env') || (copy('.env.example', '.env') && chmod('.env', 0600));\"", "@php artisan skv:bootstrap --no-interaction", "@php artisan skv:install"]`. `skv:install` also runs the bootstrap logic as an implicit step 0, so a bare `php artisan skv:install` on a clone works.

#### 5.3.4 Browser wizard runtime

- **Route**: `/welcome-setup` and its Livewire update endpoint are registered (local environment only) **without a domain constraint**, outside the tenant resolver, membership middleware and second-factor enforcement. While the marker is absent, the resolver skips resolution for every host instead of returning the tenant 404, and `/` redirects to the wizard (see access gate).
- **Access gate** (all must hold, else 404): `app()->isLocal()`; marker absent; a loopback `REMOTE_ADDR` (`127.0.0.0/8`, `::1`; an IPv4-mapped `::ffff:` address is not loopback) and no header a proxy or tunnel adds (`X-Forwarded-*`, `X-Expose-*`, `CF-*`, `Tailscale-*`, `Forwarded`, `X-Forwarded`, `Forwarded-For`, `Via`, `X-Original-Host`, `X-Original-URL`, `X-Host`, `X-Real-IP`, `True-Client-IP`, `X-Client-IP`, `Client-IP`, `X-Cluster-Client-IP`, `Fastly-Client-IP`; DEC-24, RL-4, L7b-14, M7c T10 #5 in M8a); a valid one-time setup token. `skv:bootstrap` writes a 32-byte token to `storage/app/private/skv-setup-token`. A request to `/` that passes the other conditions **and** finds no user with `is_super_admin = true` is redirected to `/welcome-setup?token=…`; the wizard checks the token with `hash_equals`, invalidates whatever session the browser brought (L7b-11) and stores the token's hash in the new (file) session. Later wizard requests are authorised by that session token, so step 2 seeding a super admin does not lock the wizard out; the token file is deleted in step 9. The address alone is no gate: under Herd every request arrives from 127.0.0.1, including `herd share` traffic, so the headers are checked as well. TrustProxies stays at its default. Spike S6 confirms which headers `herd share` adds.
- **Runtime state**: a dedicated `setup` middleware group sets `session.driver=file`, `cache.default=file` and `queue.default=sync` before `StartSession` runs, so the wizard never depends on the database that changes under it. Answers and per-step status live in `storage/app/private/skv-setup.json` (the super-admin password is hashed on entry; only the hash is stored), so a reload or 419 resumes at the first incomplete step. `SESSION_COOKIE` is fixed in `.env.example`, so writing `APP_NAME` never renames the session cookie.
- **Execution**: the wizard never uses the queue. Each step is one Livewire action call with `set_time_limit` raised; every step that touches the DB purges and reconnects so it uses the latest values. Steps with `isLong()` (frontend, Playwright, Claude) are started as a detached process (`Process::start` with `nohup`/`setsid`) writing exit code and output tail to `storage/app/private/skv-setup/{step}.json`; the page polls (`wire:poll.2s`) until it finishes (Herd's nginx has a 60 s FastCGI timeout).
- **Herd step**: because `herd secure`/`isolate` restart nginx and php-fpm and the secured vhost 301-redirects http to https, step 10 runs after the marker, as a detached process logging to `storage/logs/skv-herd.log`. The page then stops making Livewire requests and polls a server-side status endpoint on the http origin, which reads the step's exit and log files and only reports done after a server-side confirmation (`herd secured` lists the site, or a server-side http probe of the site answers 301); an https 200 alone proves nothing, because Herd's default certificate answers before the site is secured (DEC-23). The page then does a full GET navigation to a single-use signed login URL for the new super admin (or the login page for demo) on the final origin. The summary is read from the marker. If the detached process cannot start or the poll times out after 60 s, step 10 returns `manual('herd secure <name>')`, `APP_URL` stays http, and — when the user continues without securing — the passkeys module is switched off (`MODULE_PASSKEYS=false`) with a summary note on how to enable it later.
- **No Vite dependency**: the setup layout (`layouts/setup`) does not use `@vite`. It inlines a prebuilt, committed `resources/setup/setup.css` (Tailwind + Flux styles generated from the setup views; `npm run build:setup` regenerates it; CI checks it is current) and uses `@fluxAppearance`, `@fluxScripts` and `@livewireScripts`, which are served through PHP routes. The wizard renders with `public/build` absent.

**CLI**: `php artisan skv:install [--answers=JSON] [--no-interaction] [--force]` uses the same steps with Laravel Prompts (`form()`, `task()`), in the order above (the Herd step runs normally outside php-fpm).

**Spike S1 dependency**: whether a php-fpm request under Herd can run `herd`, `npm`, `git` and `claude`, and whether a detached process outlives the request and the nginx/php-fpm restart. Fallback: those steps return `manual(command)`; env, DB, seed, config and marker steps run in-process regardless.

### 5.4 Doctor

`php artisan skv:doctor [--fix] [--json]`. Each check returns `pass`, `warn`, `fail` or `skipped` with a message and the exact fix command. A check decides whether it applies from detection and the marker answers, and returns `skipped` otherwise. **Green = no `fail`.** `--fix` performs only safe repairs (`permissions:sync`, flag/role drift, `storage:link`, `core.hooksPath`, asset build). → Built (M7a–M8a): `storage:link` gets `--force` only over a wrong or dangling link and never removes a directory or a file; a missing or short `HEALTH_CHECK_KEY` is replaced by a random 40-character key, a blank `BACKUP_ARCHIVE_PASSWORD` is generated while the backups module is on, and a setup token left after setup is deleted (B21).

Checks (conditions in brackets):
- PHP ≥ 8.4; `ext-gd` present (→ warn when it cannot write WebP, which profile photos need; M8a); `APP_KEY` set.
- → `public/storage` resolves to `storage/app/public` (warn while it is missing; fail for a link elsewhere, a dangling link, a directory or a file; M8a, D63).
- Herd present (warn when absent); Herd Pro (warn when absent).
- Site served by Herd (parked under a `herd paths` entry or in `herd links`); [HTTPS on] listed in `herd secured`.
- Wildcard subdomain resolves (`probe.{apex}`); without Herd the fix text prints the `/etc/hosts` lines for the apex, `admin.` and every organisation slug.
- Apex matches `APP_URL`.
- DB reachable; migrations current; [pgsql] test DB present; warn when a `database/schema/pgsql-schema.*` dump exists and `psql`/`pg_dump` cannot be resolved.
- Permissions in sync; organisation admin role(s) present per §6.3; at least one active super admin; `is_super_admin` ↔ `super_admin` role drift.
- `SESSION_DRIVER=database`; `AuthenticateSession` registered.
- `HEALTH_CHECK_KEY` set.
- Node satisfies `^20.19 || >=22.12`; Vite manifest present and current.
- [`MAIL_MAILER=smtp`] the configured `MAIL_PORT` is listening; [log] info line (→ any other mailer passes with a message that names it, without a probe; DEC-36 (24) (d)).
- [backups on] `pg_dump` found (auto-detect `/Users/Shared/Herd/services/postgresql/*/bin`).
- [Flux Pro installed] credentials present.
- Queue connection works.
- Git hooks path set; [playwright] Playwright installed (warn).
- [claude] `CLAUDE.md` imports `@AGENTS.md` and `AGENTS.md` exists; MCP servers configured; superpowers installed (warn).
- Setup token file absent once the marker exists (warn).

The same check classes back the System page (§6.5) and the `/health-check` checks.

## 6. Architecture

### 6.1 Directory conventions

- `app/Tenancy/` — tenancy core (§6.2).
- `app/Authorization/` — `Permission`, `Role` enums, catalogue, `permissions:sync`, `withPermissionsTeam()`, `SetSuperAdmin`.
- `app/Actions/{Audit,Auth,Fortify,Invitations,Organisations,Roles,Settings,Users}/` — single-purpose action classes; Livewire components call actions, never contain domain logic.
- `app/Setup/` — steps, context, state file, wizard support, doctor checks.
- `app/Support/` — small helpers (URL, branding, locale, `Skv` facade incl. `hasFluxPro()`).
- `resources/views/pages/**` — full-page Livewire multi-file components (`pages::` namespace, the official kit's convention); `resources/views/components/**` — reusable Livewire/Blade components (DEC-05). `config/livewire.php` sets `make_command => ['type' => 'mfc', 'emoji' => false]`; existing components are converted with `livewire:convert --mfc` and their `⚡` directory names renamed (the command keeps the emoji of the source name).
- `config/skv.php` (module flags read from `MODULE_*` env, invitation and second-factor settings), `config/tenancy.php`, `config/branding.php`.

### 6.2 Tenancy core

- `CurrentTenant` scoped singleton; `Tenant` facade: `current(): ?Organisation`, `check(): bool`, `run(Organisation $org, Closure $fn)`, `bypass(Closure $fn)`, `forget()`.
- Events `TenantResolved` / `TenantForgotten`; listeners set/reset the Spatie team id and `passkeys.allowed_origins` (the RP id stays the apex, §4.2).
- `TenantResolver` interface with a `SubdomainResolver`; slug lookup cached, invalidated by the organisation observer. Reserved slugs and the admin subdomain are never resolved as tenants.
- **Host scoping**: `Route::tenant(fn)` and `Route::central(fn)` are route groups that attach `EnsureTenantHost` / `EnsureCentralHost` middleware — they do **not** use `Route::domain()`, so route names, `route()` calls and `mount()` signatures carry no `{tenant}` parameter. Both middleware are registered with `Livewire::addPersistentMiddleware()` and placed before `can:` in the middleware priority. Only single-host routes go in these groups; shared routes keep one name. Component actions that need a particular host keep an explicit guard (`Tenant::check()` / `#[RequiresTenant]`), each covered by a forged `/livewire/update` test from the wrong host.
- **Route × host matrix** (normative for M2–M5):

| Route | Host | Notes |
|---|---|---|
| `/` | any | guest → login; tenant host → dashboard; super admin on central → organisations index; before setup → wizard (§5.3.4) |
| `dashboard`, `users.index`, `users.edit`, `invitations.pending`, `roles.index`, `organisations.index`, `organisations.edit`, `activity.index`, `activity.export`, `settings.*`, `system.index` | any | on central hosts only super admins pass (membership middleware); pages read tenant models through `App\Tenancy\HostScope::read()` (DEC-28) and central views show an organisation column/filter |
| `users.invite`, `invitations.bulk` | any | on central an organisation picker is required |
| `organisations.create` | central | the organisation wizard; tenant hosts answer 404 (DEC-28) |
| role create | tenant, or central with an explicitly picked organisation | |
| impersonation start (a `#[RequiresTenant]` Livewire action on `users.index`, not a route, DEC-28) | tenant | module on |
| `impersonation.stop` | any | module on |
| `invitations.accept` | the invitation's tenant host | `signed:relative` |
| `/auth/handoff/{token}` (GET; POST `auth.handoff.store` confirms replacing another signed-in user's session, DEC-28) | any | bound to target host |
| Fortify / passkey routes, `.well-known/passkey-endpoints` | any | host-scoped login rule |
| `/up`, `/health-check` | any | stateless |
| `/welcome-setup` | any | local, before setup only |

  A Pest dataset test covers every named route × {tenant, apex, admin} × {guest, member, org admin, super admin} with the expected status or redirect.
- **Strict mode** (`config('tenancy.strict')`): querying a tenant model with no tenant bound throws `TenantNotResolvedException`. It applies to HTTP and Livewire requests and to queued jobs that carry a `tenant_id`. Artisan commands, scheduled tasks, seeders, migrations, setup steps, doctor checks and `/health-check` run in central (bypass) context by default (via a `CommandStarting` listener and explicit wrapping); commands that work per organisation iterate with `Tenant::run()`. On central hosts, reads of tenant models must use `Tenant::bypass()` explicitly; the unscoped auth user provider is exempt by design; the cascade runs in bypass. An arch test limits `Tenant::bypass()` to `App\Console`, `App\Setup`, `App\Tenancy`, `App\Actions\Audit`, `Database\Seeders` and the health controller. Livewire pages are not on that list: any-host pages read tenant models through `App\Tenancy\HostScope::read()` (scoped on a tenant host; `Tenant::bypass()` inside `App\Tenancy` for super admins on central hosts) and filter central models with `HostScope::organisationId()` (DEC-28).
- **Queue tenant context**: `Queue::createPayloadUsing(fn () => ['tenant_id' => Tenant::current()?->id])` adds the tenant to every payload (jobs, queued mailables, notifications, listeners). A `JobProcessing` listener binds it before the command is unserialized (so model restore and `loadMissing()` already run under the right tenant); a missing or soft-deleted organisation fails the job without retry. `JobProcessed` / `JobFailed` / `JobExceptionOccurred` call `Tenant::forget()`. A payload without `tenant_id` runs centrally.
- `tenant_url(Organisation|string $slug, string $path = '/')` and `Hosts::url()` take the scheme and the port from `APP_URL`, in requests, workers and the console alike; a request's port and `X-Forwarded-Proto` / `X-Forwarded-Port` never reach the links built with them (DEC-34). A page's own links, form actions and redirects on its host still come from the request (`route()`, `url()`), so behind a proxy `TRUSTED_PROXIES` remains required for the client IP and for those links' host, scheme and port. Signed accept URLs are built with it and tested from a worker context.
- Soft-delete cascade over `config('tenancy.tenant_models')` (includes `Activity`); an arch test asserts every model with `organisation_id` uses the trait and is listed. Activity rows with `organisation_id = null` (central events) are visible only in central views.

### 6.3 Authorization

- `Permission` backed enum: `label()`, `description()`, `group()`, `superOnly()`. `Role` enum for the system roles `super_admin` and `organisation_admin`.
- **Super admin**: `users.is_super_admin` is the only source of truth; `User::isSuperAdmin()` reads only this column. Every super-admin rule uses it: `Gate::before`, login on any host (password, 2FA, passkeys), the impersonation matrix, the last-super-admin guard, the doctor check, the global second-factor flag. The `super_admin` role is a display badge only: protected, not assignable through `UpdateUserRoles`, and kept in sync by the `SetSuperAdmin` action (used by the users edit page, `skv:create-super-admin` and seeders), which sets the flag and attaches/detaches the role in one transaction and enforces the last-super-admin guard (counting active, non-deleted users with the flag). `permissions:sync` and doctor `--fix` repair drift.
- `permissions:sync`: upserts the catalogue, maintains the organisation admin role(s) per the S2 outcome, prunes removed permissions. Runs in setup, on deploy, and via doctor `--fix`.
- `withPermissionsTeam(?int $teamId, Closure $fn)` with `finally`; an arch test bans `setPermissionsTeamId()` elsewhere.
- **Spike S2** decides between (A) one global `organisation_admin` template role (`team_id = NULL`) assigned per team and (B) one role row per organisation (skv2 D8). Consequences:
  - `UpdateUserRoles`: under A the only accepted null-team role is `organisation_admin`, always attached with the target organisation's team id; under B every null-team role is rejected.
  - `permissions:sync`: A upserts the single template; B (re)creates and resyncs every organisation's role, and the organisation observer creates it on create.
  - Doctor: A checks the template exists with the current permission set; B checks every organisation has its role.
  - Roles index: under A the template is protected like `super_admin` (it already is as a system role).
  The M2 plan is written after S2; the outcome is recorded in `docs/decisions.md`.

### 6.4 Cross-host handoff

Super admins (and slug renames) move between hosts with a single-use token, stored as a sha256 hash in the central `handoff_tokens` table instead of a signed URL (DEC-27 (8)): `/auth/handoff/{token}` on the target host, valid 60 seconds, bound to the user and target host, consumed on use, audited. A link opened by the user who is already signed in continues without a new sign-in; a link opened while another user is signed in asks first, and only the confirming POST replaces this browser's session (DEC-28). Session cookies stay host-only. → Bound to the password (M8a, DEC-36 (3)): the token row stores `SessionGuard::hashPasswordForCookie()` of the user's password hash (`handoff_tokens.password_hash`), and a missing or different value is refused, so a password change or reset on any path ends the links issued before.

### 6.6 v1 extras (DEC-11)

- **Sessions**: Settings → Security lists the user's rows from `sessions` (device and browser parsed from `user_agent` by a small in-house parser, IP, last active, "this device"). "Log out other devices" requires the password: `Auth::logoutOtherDevices($password)` (rehashes the password and refreshes this device's remember cookie), then delete the user's other `sessions` rows. Remember-me logins elsewhere are cut off because `AuthenticateSession` runs on every authenticated request (§4.2). Audited. Tests: a second "remember me" client is unauthenticated on its next request; the current device stays logged in; other rows are gone. → Built in M7d (DEC-35 (2)): the action is limited to 5 attempts per minute per user (`UserActionLimit::logoutOtherDevices()`), counted before the password is checked, and needs no extra password confirmation, because it checks the password itself. Only rows within the session lifetime are listed; "log out other devices" deletes every other row of the user and the user's unused handoff tokens, and records `security.other_sessions_ended` with `properties.count`, the number of rows deleted. Rows are identified to the client by a keyed hash (`hash_hmac('sha256', $id, app.key)`), never by the session id. During an impersonation the section is hidden and every request to it answers 403. → M8a (CD-18, DEC-36 (18)): "log out other devices" also gives this device a new session id inside the same transaction (`session()->migrate()`, and its `sessions` row moves to the new id), so a copy of this browser's session cookie is signed out too; the CSRF token stays.
- **Second factor required per organisation**: `organisations.require_second_factor` (default false), editable by organisation admins and super admins, audited. Tests: redirect from the dashboard; password confirmation without a loop; enabling TOTP and, separately, registering a passkey; dashboard reachable afterwards; navigating away is blocked; module-off case. → Built in M7d (DEC-35 (3), (4)): the middleware is appended to the `auth` groups of `routes/web.php`, `routes/settings.php` and `routes/admin.php`. Livewire requests are recognised by route name (`*livewire.update`, `livewire.upload-file`, `livewire.preview-file`), never by the `X-Livewire` header. An unsatisfied GET or HEAD is redirected; any other method gets a 403 (a blocked Livewire update is replayed against its page's GET and is redirected too). The security page shows the explanation as a callout; super admins get their own message. A passkey satisfies the rule as the factor of the sign-in: Fortify challenges only a confirmed TOTP secret after the password, so the password sign-in of a user the rule applies to whose only factor is a passkey is refused once the password is right, and they sign in with the passkey (DEC-35, final review). → M8a: during an impersonation the security page shows no second-factor callout (E35).
- **Audit CSV export**: streamed download honouring the current filters and tenant scope; gated by `activity_log.view`; audited. → Built in M7d (DEC-35 (5)): the route `activity.export` (`activity/export`, any host like `activity.index`) with `can:` `activity_log.view` and the named limiter `activity-export` (5 per minute per user). Columns: date (ISO 8601, app time zone), event key, event label, causer, subject, organisation (central hosts only), IP address, user agent and properties (JSON); IP address and user agent are empty where the viewer hides them (RL-7), and there is no change-summary column. The file starts with a UTF-8 BOM; a formula guard puts `'` before `=`, `+`, `-`, `@`, a tab or a CR (and the full-width ＝＋－＠) at the start of a cell and after a `;`, tab, CR or LF inside it. `audit.exported` is recorded before streaming, with `properties.filters`. It streams with `streamDownload()` and `lazyById(500)` inside `HostScope::read()`; it is not a Livewire download.
- **Bulk invitations**: paste addresses or upload a CSV (email, optional locale) via `flux:input type="file"` + `WithFileUploads`; per-row validation; preview; result summary (sent / skipped with reason); reuses the invite action; queued mails. → Built in M7d (DEC-35 (6)): pasted addresses (one per line, or separated by commas or semicolons; at most 30,000 characters) and a CSV (`file|mimes:csv,txt|max:512`: an email column and an optional locale column; a header row is optional and recognised only by its names: a first row with no `@` in any cell and a cell that contains `mail` without a dot or is `locale`, `language`, `lang` or `taal`; comma- or semicolon-separated; a UTF-8 BOM is stripped), at most 100 rows together.
